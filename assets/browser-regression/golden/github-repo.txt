	<td> Build JavaScriptCore and ICU from source in bun's own build graph on … </td>
		[1821]<a title='Build JavaScriptCore and ICU from source in bun's own build graph on every target (#41330)

JavaScriptCore, WTF, bmalloc — and, on every target except macOS, ICU —
are compiled from source inside bun's own ninja graph, like every other
vendored dependency, instead of being downloaded as a prebuilt
`bun-webkit-*` tarball. This is the default for every build, local and
CI; `--webkit=prebuilt` remains as an explicit opt-in.

### What changes

**CI**
- All 13 `build-bun` lanes (Linux x64/arm64 glibc + baseline + musl +
ASAN, Android, FreeBSD, macOS x64/arm64, Windows x64/arm64) compile JSC
in the same graph as bun's own C++; no
`libJavaScriptCore.a`/`libWTF.a`/`libbmalloc.a` step — the objects go
straight into the same archive/link as bun's.
- A WebKit change no longer needs a prebuilt to be published before bun
can build against it: bump `WEBKIT_VERSION` to any commit pushed to
oven-sh/WebKit.
- `build-bun` steps take ~1–2.5 min longer per target. Binary sizes: see
the table below (nothing grew; FreeBSD/Android −13 MB from ICU data
packing, windows-arm64 −3.5 MB, the rest under 2 MB).
- Build images: `bootstrap.sh` v42 adds `flex`/`bison` (host `migcom`
for the macOS lanes). Linux images are baked as a Buildkite job on a
fresh machine of the target distro plus a `wait-for-image` step, instead
of an instance driven over SSH from the hosted agent.
- `build-bun` is a plain full build now (the `archive-link` mode is
removed): bun's objects go straight into the link as in a local build,
and the per-lane `libbun-*.a.gz` / `libbun_runtime.a.gz` / dep-lib
artifact uploads, which nothing consumed, are gone. `cpp-only` keeps its
archive for the split pipeline. The precompiled header is built whenever
C++ is compiled (previously skipped for CI + full).
- `bootstrap.ps1` v23: ruby and zstd for native from-source builds on
the Windows images, and LLVM 21.1.8 installed from its release installer
(scoop's `llvm@21.1.8` now generates a non-existent `.msi` URL).
- Buildkite canvas: `verify-baseline` and `trace-order` are drawn beside
each target's build group instead of inside it (from #41408; no
scheduling change).

**Local development**
- `bun bd` / `bun run build` compile JSC too (fetched by ninja like
every dep, ~35 MB sparse; the first build of a build dir pays ~2 min for
JSC, then it is incremental and ccache-friendly). Host tools needed:
`ruby`, `python3`, `perl` (JSC's generators), `zstd` (ICU data,
non-macOS targets), and `flex`/`bison` only when cross-compiling a macOS
target from Linux (a Mac uses Xcode's `mig`).
- Release builds are LTO by default everywhere (what CI ships);
`--lto=off` for fast relinks. The `btg` profile is gone (it was "release
+ LTO"). On a native macOS or Windows host whose rustc LLVM is newer
than clang's (today: nightly LLVM 22 vs Homebrew llvm@21), the Rust↔C++
cross-language step is skipped and each half LTOs on its own — Apple's
ld runs LTO through clang's libLTO, which can't read newer bitcode and
has no lld to swap in; CI cross-compiles both from Linux with rustc's
lld and keeps full cross-language LTO.
- Working on JSC itself: `--local-deps=WebKit=<your clone>` on any
profile, like every other dep; `bun run build:local` is that with
`$BUN_WEBKIT_PATH`. The `debug-local`/`release-local` profiles and the
nested-cmake WebKit build are removed. `vendor/WebKit` is the build's
own fetch, so clones live elsewhere.
- Upgrading WebKit: the build itself checks the fetched tree against
what `scripts/build/deps/webkit.ts` transcribes — `Sources.txt` against
the checked-in unified-bundle lists, and a canonical rendering of the
relevant CMake statements (generators, options, compiler flags) against
`webkit-cmake.snapshot` — and fails with a diff when a bump changes
them; `.claude/commands/upgrade-webkit.md` says where each kind of
change maps.

### How it works

- **One dep kind.** Every C/C++ dep is a `direct` spec in
`scripts/build/deps/*.ts`: source groups (each with its own
flags/includes/PCH), `steps` (generators, host tools, target
executables), `headers` (files written at configure). WebKit is the same
shape as zlib, just larger; the `custom` kind is gone.
- **WebKit** (`deps/webkit.ts` +
`deps/webkit-{bmalloc,wtf,jsc,llint,inspector}-sources.ts`): bmalloc,
WTF and JavaScriptCore as three source groups; JSC's TUs are the unified
bundles listed explicitly in `webkit-sources.ts` (as WebKit's bundler
forms them, regenerated on a bump) plus the `@no-unify` files; every
generator WebKit's cmake runs (create_hash_table LUTs,
bytecode/Air/yarr/wasm generators, JS builtins, inspector protocol,
GeneratePreferences, offlineasm via the two LLInt extractor executables,
MIG on macOS) is a step invoking the same script with the same
arguments; `cmakeconfig.h`, the `<JavaScriptCore/X.h>` / `<bmalloc/X.h>`
forwarding stubs and the bundle files are `headers` entries. Compile
flags reproduce OptionsJSCOnly / WebKitCompilerFlags / OptionsMSVC per
platform on top of bun's dep-global flags, so JSC gets bun's `-march`,
LTO, sanitizer and hardening settings. Nothing reads the WebKit tree at
configure time.
- **ICU** (`deps/icu.ts` + `deps/icu-sources.ts`, `icu-data.ts`):
`common`/`i18n` compiled in-graph; a host `icupkg`; the data file
filtered and its display-name items zstd-repacked with a trained
dictionary, decompressed on first use through
`src/jsc/bindings/bun_icu_decompress.cpp`. That scheme was already in
the Linux/Windows prebuilts; it now applies uniformly (Linux, musl,
Android, FreeBSD, Windows). macOS keeps the SDK's `libicucore`.
- **Link-time checks** run as ninja validations of bun's link on every
lane, all static (`scripts/build/verify-binary.ts`, expectations per
target in `binary-expectations.ts`): exported symbols vs the lists in
`src/`; the exact NEEDED / dylib / import-DLL set and the glibc (2.17) /
FBSD (1.7) symbol-version ceiling (un-numbered version nodes such as
`GLIBC_ABI_DT_RELR` count; Android's floor is bionic's `LIBC`…`LIBC_P` /
`LIBLOG`…`LIBLOG_O`, API 28); forbidden imports (`__cxa_throw`,
`__emutls_*`, …); every static initializer symbolized and matched
against the runtime's known ones (none may come from bun/JSC/WTF);
nx-stack / no-RWX / PIE / DllCharacteristics; debug-info shape; and no
symbol strongly defined by two link inputs (every input must be readable
by the scanning tool — under the rustc/clang LLVM skew the scan uses
rustup's `llvm-nm`, hence the `llvm-tools` component in
`rust-toolchain.toml`). Plus the existing `--revision` smoke test
(host-runnable targets only) and the JSC ClassInfo audit.
- **testFFI** (JSC's bun:ffi ABI test program) is compiled and linked by
`bun.ts` next to `bun` from the same objects and shipped in the CI
artifact; the test fails, not skips, if it is missing in CI.
- **Native macOS and Windows hosts** (which CI never exercises — every
lane cross-compiles from Linux) were built end to end: Xcode's `mig`,
clang-cl as the target compiler with clang as the host compiler, ICU
data packing and testFFI all work there.
- **Cross targets** build from the Linux agents as before: macOS with
the SDK plus Apple's `migcom` built for the host
(`deps/bootstrap-cmds.ts`), Windows with clang-cl and the auto-fetched
MSVC sysroot, FreeBSD/Android with their sysroots. macOS and Windows
hosts work too.
- **Linking without archives.** bun's own objects and the dependencies'
objects go straight to the link; no `libbun-*.a`, no per-dep
`.a`/`.lib`. The dep objects are a lazy group (`link()`'s `lazyObjects`:
lld's `/start-lib … /end-lib`, i.e. taken only if referenced — a static
library's semantics minus the file). That matters on Windows: COFF
linkers discard unreferenced code only at COMDAT granularity, so an
object with plain sections that nothing calls (any NASM output —
BoringSSL's AES-GCM-SIV asm is never called on Windows by BoringSSL's
own design) would otherwise be linked whole; upstream and Chromium rely
on archive member selection for the same thing. The group reaches
lld-link through clang-cl as `/clang:-Wl,@<exe>.lazy.rsp`. On ELF/Mach-O
the objects simply follow bun's in `$in` (those linkers dead-strip per
section).
- **Windows: `/lld-allow-duplicate-weak`.** WTF/JSC reference bun's
hooks (`WTFTimer__*`, `Bun__errorInstance__finalize`,
`Bun__reportUnhandledError`) as `__attribute__((weak))`; COFF has no
weak undefined symbol, so each referencing TU carries a weak external
with its own absolute-0 default and lld-link (MSVC mode) reports two
such TUs as a duplicate symbol even though bun's strong definition wins
— which ThinLTO importing `RunLoop::TimerBase::start()` into a JSC
module produces. lld-link's switch for exactly that check is on for
bun's and the JSC test programs' links (the latter previously used
`/force:multiple`); duplicate *strong* definitions still error. It
becomes a no-op once lld-link accepts several weak references to one
symbol (fixed in bun's LLVM toolchain) and is to be dropped then.

Build-system changes that came along:
- `ninja.ts` declares every build-dir output under its absolute path as
well, so a header a compiler depfile names absolutely resolves to its
generator and its includers recompile in the same run (was one build
late; affected bun's own `codegen/` too).
- `ninja_required_version` is 1.11 (validations). One phony per
order-only group instead of repeating generated-header lists on every
compile edge.
- One `dep_codegen` rule (`stream.ts --cwd/--env/--stdout`) for all dep
generators; `host_cc`/`host_cxx`/`host_link` for host tools;
`hostCc`/`hostCxx` are the plain clang drivers for any Windows target;
`-fsanitize=address` is part of the target link flags; tarball sources
carry a `sha256`; dep fetches print `[name] … (elapsed)`.
- Tools that assumed a prebuilt layout now read the build:
`scripts/jsc-exception-lint` takes JSC's TUs from
`compile_commands.json`; `bun-inspector-protocol`'s generator reads our
`CombinedDomains.json`; `.vscode/c_cpp_properties.json` just points at
the compile database.

### Bugs and misconfigurations on main that this fixes

Found by diffing compile lines against WebKit's cmake and dissecting
main's release binaries target by target:

- **windows-arm64: JSC compiled with FP contraction.** JSC's CMakeLists
sets `-ffp-contract=off -fno-slp-vectorize` for the whole target;
clang-cl ignores the GNU spellings and cmake's probe dropped them, so
the Windows prebuilt never had them. On arm64 that fused `Date`
arithmetic (`setNewValueFromTimeArgs`, `millisecondsFromComponents`,
`dateProtoFuncSetYear`, …) into `fmadd`, i.e. different rounding than
every other platform and than the JIT. Now passed as
`/clang:-ffp-contract=off /clang:-fno-slp-vectorize`.
- **Stack protector depended on the host compiler's vendor default.**
Nothing stated a policy, so CI (apt.llvm.org clang) shipped without it
while a build on Arch/Alpine/Fedora-packaged clang got
`-fstack-protector-strong` in every eligible function (62k canary checks
vs 161), and the musl JSC prebuilt (Alpine clang) had it while no other
target did. `-fno-stack-protector` is now explicit on unix.
- **PIC depended on the host compiler's default for deps.** bun's own
objects were `-fno-pic`, vendored deps got whatever the building clang
defaults to. CI's clang defaults to non-PIE so release artifacts were
unaffected, but on hosts whose clang defaults to PIE (Arch, Fedora,
Alpine, Homebrew) every dep was PIC: `.data.rel.ro` 541 KB instead of
109 KB and 4–7% more pages touched at startup. Every dep now gets bun's
PIC policy explicitly.
- **windows-arm64 tuned for Ampere.** `-mtune=ampere1` (copied from the
Linux server lane) padded every function and loop to 64 bytes on
Snapdragon hardware; MSVC, Chromium and Rust use generic tuning there.
Dropped; `-march=armv8-a+crc` unchanged.
- **Windows: the exe's import library overwrote the object archive.**
`bun.exe` exports symbols, so lld-link wrote `bun-profile.lib`, the same
path as the object archive `cpp-only` mode produces. It now goes to
`obj/<exe>.import.lib`.
- **Generated headers were one build late.** A generated header named
absolutely in a depfile didn't match its relative ninja output, so
includers recompiled on the *next* run (bun's `codegen/` headers too).
Fixed in `ninja.ts` as above.
- **FreeBSD/Android shipped 13 MB of ICU data they never load.** Only
the Linux and Windows prebuilts filtered and compressed ICU data; every
non-macOS target now does.
- **With a warm ccache, the second build of a fresh build dir recompiled
hundreds of objects (macOS, Windows).** The build exported
`CCACHE_FILECLONE=1`; entries stored that way are raw files, and a hit
is materialized by clone (APFS) or CopyFile (Windows), both keeping the
entry's mtime, so objects came out older than headers generated in the
same run. Dropped, plus `CCACHE_NAMESPACE=bun` so the raw entries
already in everyone's cache are never hit again.
- **`bun run build` never reached a no-op with an isolated-layout
`node_modules`.** The install edge declared
`node_modules/<dep>/package.json` as outputs; ninja pre-creates output
directories, so `node_modules/<dep>/` existed before `bun install` ran,
bun's isolated linker skipped the symlink, and install (plus the
esbuild/cargo edges behind it) re-ran on every build. It now declares
the `node_modules/<dep>` entry itself.
- **Links were serialized through ninja's console pool.** `link` was a
`pool = console` rule (depth 1), so once the graph had more than one
executable (bun, testFFI, JSC's LLInt extractors) bun's link waited
behind the others — ~25 s per release lane. Links are ordinary edges
now; the smoke test and ClassInfo check became ninja validations of the
link.
- **Every build after a build-script edit configured twice.** ninja
judges its `regen` edge by the mtime it recorded for `build.ninja`, not
the file's, so the manifest build.ts had just refreshed still looked
stale and ninja ran configure again (`[0/1] reconfigure`). Configure now
stamps the manifest and `ninja -t restat`s it.
- **bun.exe exported bmalloc's API and libpas' `g_config`.** bmalloc's
`BEXPORT` is `__declspec(dllexport)` even in a static build (WTF's macro
has the fork's carve-out, bmalloc's doesn't); 23 stray exports on top of
the intended Node-API/V8/libuv/llhttp set (same on main's prebuilt).
Found by the new export check; fixed with `-DBEXPORT=`.
- **Debug builds ran ~93 static initializers from the generated
classes.** `ZigGeneratedClasses.cpp` initialized each `extern "C"
<Type>__ptrOffset` from a non-`constexpr` `offsetOfWrapped()`; `-O2`
folded them, `-O0` ran them at startup. `constexpr` now, so they're
constant-initialized in every build (found by the new initializer
audit).
- **bun.exe ran in the Windows Vista compatibility context.** Its
manifest had no `<compatibility>`/`<trustInfo>` section, so Windows
applied Vista-era behavior (version APIs capped at 6.2, PCA monitoring)
to bun and every addon in-process. Now declares Windows 7–11 and
`asInvoker`, like node.exe; one visible effect is `process.report`'s
`header.osRelease` reporting `10.0` instead of `6.1` on Windows 10/11
(`os.release()` was already right, it uses `RtlGetVersion`). Found by
comparing against node's binaries.
- **Linux/FreeBSD exported four bun-internal `napi_internal_*` helpers**
through the `napi*` glob in the version script (macOS/Windows didn't).
Renamed out of the `napi_` namespace.
- **WebKit's own warning set wasn't applied when compiling it** (once
JSC is built here rather than by cmake): `-Wall -Wextra …
-Werror=undefined-inline/-internal` and the `-Wno-*` upstream carries
(e.g. clang 21's `-Wcharacter-conversion`) now match
WebKitCompilerFlags.cmake / OptionsMSVC.cmake.

- **Windows x64 / arm64 — runtime behavior change**: `bun.exe`'s

every native addon it loads) in the Vista compatibility context:

- **Linux / FreeBSD**: 4 fewer exports (`napi_internal_*`).
- **All targets**: `testFFI[.exe]` ships next to `bun-profile` in the

JavaScriptCore, WTF, bmalloc — and, on every target except macOS, ICU —
are compiled from source inside bun's own ninja graph, like every other
vendored dependency, instead of being downloaded as a prebuilt
`bun-webkit-*` tarball. This is the default for every build, local and
CI; `--webkit=prebuilt` remains as an explicit opt-in.

### What changes

**CI**
- All 13 `build-bun` lanes (Linux x64/arm64 glibc + baseline + musl +
ASAN, Android, FreeBSD, macOS x64/arm64, Windows x64/arm64) compile JSC
in the same graph as bun's own C++; no
`libJavaScriptCore.a`/`libWTF.a`/`libbmalloc.a` step — the objects go
straight into the same archive/link as bun's.
- A WebKit change no longer needs a prebuilt to be published before bun
can build against it: bump `WEBKIT_VERSION` to any commit pushed to
oven-sh/WebKit.
- `build-bun` steps take ~1–2.5 min longer per target. Binary sizes: see
the table below (nothing grew; FreeBSD/Android −13 MB from ICU data
packing, windows-arm64 −3.5 MB, the rest under 2 MB).
- Build images: `bootstrap.sh` v42 adds `flex`/`bison` (host `migcom`
for the macOS lanes). Linux images are baked as a Buildkite job on a
fresh machine of the target distro plus a `wait-for-image` step, instead
of an instance driven over SSH from the hosted agent.
- `build-bun` is a plain full build now (the `archive-link` mode is
removed): bun's objects go straight into the link as in a local build,
and the per-lane `libbun-*.a.gz` / `libbun_runtime.a.gz` / dep-lib
artifact uploads, which nothing consumed, are gone. `cpp-only` keeps its
archive for the split pipeline. The precompiled header is built whenever
C++ is compiled (previously skipped for CI + full).
- `bootstrap.ps1` v23: ruby and zstd for native from-source builds on
the Windows images, and LLVM 21.1.8 installed from its release installer
(scoop's `llvm@21.1.8` now generates a non-existent `.msi` URL).
- Buildkite canvas: `verify-baseline` and `trace-order` are drawn beside
each target's build group instead of inside it (from #41408; no
scheduling change).

**Local development**
- `bun bd` / `bun run build` compile JSC too (fetched by ninja like
every dep, ~35 MB sparse; the first build of a build dir pays ~2 min for
JSC, then it is incremental and ccache-friendly). Host tools needed:
`ruby`, `python3`, `perl` (JSC's generators), `zstd` (ICU data,
non-macOS targets), and `flex`/`bison` only when cross-compiling a macOS
target from Linux (a Mac uses Xcode's `mig`).
- Release builds are LTO by default everywhere (what CI ships);
`--lto=off` for fast relinks. The `btg` profile is gone (it was "release
+ LTO"). On a native macOS or Windows host whose rustc LLVM is newer
than clang's (today: nightly LLVM 22 vs Homebrew llvm@21), the Rust↔C++
cross-language step is skipped and each half LTOs on its own — Apple's
ld runs LTO through clang's libLTO, which can't read newer bitcode and
has no lld to swap in; CI cross-compiles both from Linux with rustc's
lld and keeps full cross-language LTO.
- Working on JSC itself: `--local-deps=WebKit=<your clone>` on any
profile, like every other dep; `bun run build:local` is that with
`$BUN_WEBKIT_PATH`. The `debug-local`/`release-local` profiles and the
nested-cmake WebKit build are removed. `vendor/WebKit` is the build's
own fetch, so clones live elsewhere.
- Upgrading WebKit: the build itself checks the fetched tree against
what `scripts/build/deps/webkit.ts` transcribes — `Sources.txt` against
the checked-in unified-bundle lists, and a canonical rendering of the
relevant CMake statements (generators, options, compiler flags) against
`webkit-cmake.snapshot` — and fails with a diff when a bump changes
them; `.claude/commands/upgrade-webkit.md` says where each kind of
change maps.

### How it works

- **One dep kind.** Every C/C++ dep is a `direct` spec in
`scripts/build/deps/*.ts`: source groups (each with its own
flags/includes/PCH), `steps` (generators, host tools, target
executables), `headers` (files written at configure). WebKit is the same
shape as zlib, just larger; the `custom` kind is gone.
- **WebKit** (`deps/webkit.ts` +
`deps/webkit-{bmalloc,wtf,jsc,llint,inspector}-sources.ts`): bmalloc,
WTF and JavaScriptCore as three source groups; JSC's TUs are the unified
bundles listed explicitly in `webkit-sources.ts` (as WebKit's bundler
forms them, regenerated on a bump) plus the `@no-unify` files; every
generator WebKit's cmake runs (create_hash_table LUTs,
bytecode/Air/yarr/wasm generators, JS builtins, inspector protocol,
GeneratePreferences, offlineasm via the two LLInt extractor executables,
MIG on macOS) is a step invoking the same script with the same
arguments; `cmakeconfig.h`, the `<JavaScriptCore/X.h>` / `<bmalloc/X.h>`
forwarding stubs and the bundle files are `headers` entries. Compile
flags reproduce OptionsJSCOnly / WebKitCompilerFlags / OptionsMSVC per
platform on top of bun's dep-global flags, so JSC gets bun's `-march`,
LTO, sanitizer and hardening settings. Nothing reads the WebKit tree at
configure time.
- **ICU** (`deps/icu.ts` + `deps/icu-sources.ts`, `icu-data.ts`):
`common`/`i18n` compiled in-graph; a host `icupkg`; the data file
filtered and its display-name items zstd-repacked with a trained
dictionary, decompressed on first use through
`src/jsc/bindings/bun_icu_decompress.cpp`. That scheme was already in
the Linux/Windows prebuilts; it now applies uniformly (Linux, musl,
Android, FreeBSD, Windows). macOS keeps the SDK's `libicucore`.
- **Link-time checks** run as ninja validations of bun's link on every
lane, all static (`scripts/build/verify-binary.ts`, expectations per
target in `binary-expectations.ts`): exported symbols vs the lists in
`src/`; the exact NEEDED / dylib / import-DLL set and the glibc (2.17) /
FBSD (1.7) symbol-version ceiling (un-numbered version nodes such as
`GLIBC_ABI_DT_RELR` count; Android's floor is bionic's `LIBC`…`LIBC_P` /
`LIBLOG`…`LIBLOG_O`, API 28); forbidden imports (`__cxa_throw`,
`__emutls_*`, …); every static initializer symbolized and matched
against the runtime's known ones (none may come from bun/JSC/WTF);
nx-stack / no-RWX / PIE / DllCharacteristics; debug-info shape; and no
symbol strongly defined by two link inputs (every input must be readable
by the scanning tool — under the rustc/clang LLVM skew the scan uses
rustup's `llvm-nm`, hence the `llvm-tools` component in
`rust-toolchain.toml`). Plus the existing `--revision` smoke test
(host-runnable targets only) and the JSC ClassInfo audit.
- **testFFI** (JSC's bun:ffi ABI test program) is compiled and linked by
`bun.ts` next to `bun` from the same objects and shipped in the CI
artifact; the test fails, not skips, if it is missing in CI.
- **Native macOS and Windows hosts** (which CI never exercises — every
lane cross-compiles from Linux) were built end to end: Xcode's `mig`,
clang-cl as the target compiler with clang as the host compiler, ICU
data packing and testFFI all work there.
- **Cross targets** build from the Linux agents as before: macOS with
the SDK plus Apple's `migcom` built for the host
(`deps/bootstrap-cmds.ts`), Windows with clang-cl and the auto-fetched
MSVC sysroot, FreeBSD/Android with their sysroots. macOS and Windows
hosts work too.
- **Linking without archives.** bun's own objects and the dependencies'
objects go straight to the link; no `libbun-*.a`, no per-dep
`.a`/`.lib`. The dep objects are a lazy group (`link()`'s `lazyObjects`:
lld's `/start-lib … /end-lib`, i.e. taken only if referenced — a static
library's semantics minus the file). That matters on Windows: COFF
linkers discard unreferenced code only at COMDAT granularity, so an
object with plain sections that nothing calls (any NASM output —
BoringSSL's AES-GCM-SIV asm is never called on Windows by BoringSSL's
own design) would otherwise be linked whole; upstream and Chromium rely
on archive member selection for the same thing. The group reaches
lld-link through clang-cl as `/clang:-Wl,@<exe>.lazy.rsp`. On ELF/Mach-O
the objects simply follow bun's in `$in` (those linkers dead-strip per
section).
- **Windows: `/lld-allow-duplicate-weak`.** WTF/JSC reference bun's
hooks (`WTFTimer__*`, `Bun__errorInstance__finalize`,
`Bun__reportUnhandledError`) as `__attribute__((weak))`; COFF has no
weak undefined symbol, so each referencing TU carries a weak external
with its own absolute-0 default and lld-link (MSVC mode) reports two
such TUs as a duplicate symbol even though bun's strong definition wins
— which ThinLTO importing `RunLoop::TimerBase::start()` into a JSC
module produces. lld-link's switch for exactly that check is on for
bun's and the JSC test programs' links (the latter previously used
`/force:multiple`); duplicate *strong* definitions still error. It
becomes a no-op once lld-link accepts several weak references to one
symbol (fixed in bun's LLVM toolchain) and is to be dropped then.

Build-system changes that came along:
- `ninja.ts` declares every build-dir output under its absolute path as
well, so a header a compiler depfile names absolutely resolves to its
generator and its includers recompile in the same run (was one build
late; affected bun's own `codegen/` too).
- `ninja_required_version` is 1.11 (validations). One phony per
order-only group instead of repeating generated-header lists on every
compile edge.
- One `dep_codegen` rule (`stream.ts --cwd/--env/--stdout`) for all dep
generators; `host_cc`/`host_cxx`/`host_link` for host tools;
`hostCc`/`hostCxx` are the plain clang drivers for any Windows target;
`-fsanitize=address` is part of the target link flags; tarball sources
carry a `sha256`; dep fetches print `[name] … (elapsed)`.
- Tools that assumed a prebuilt layout now read the build:
`scripts/jsc-exception-lint` takes JSC's TUs from
`compile_commands.json`; `bun-inspector-protocol`'s generator reads our
`CombinedDomains.json`; `.vscode/c_cpp_properties.json` just points at
the compile database.

### Bugs and misconfigurations on main that this fixes

Found by diffing compile lines against WebKit's cmake and dissecting
main's release binaries target by target:

- **windows-arm64: JSC compiled with FP contraction.** JSC's CMakeLists
sets `-ffp-contract=off -fno-slp-vectorize` for the whole target;
clang-cl ignores the GNU spellings and cmake's probe dropped them, so
the Windows prebuilt never had them. On arm64 that fused `Date`
arithmetic (`setNewValueFromTimeArgs`, `millisecondsFromComponents`,
`dateProtoFuncSetYear`, …) into `fmadd`, i.e. different rounding than
every other platform and than the JIT. Now passed as
`/clang:-ffp-contract=off /clang:-fno-slp-vectorize`.
- **Stack protector depended on the host compiler's vendor default.**
Nothing stated a policy, so CI (apt.llvm.org clang) shipped without it
while a build on Arch/Alpine/Fedora-packaged clang got
`-fstack-protector-strong` in every eligible function (62k canary checks
vs 161), and the musl JSC prebuilt (Alpine clang) had it while no other
target did. `-fno-stack-protector` is now explicit on unix.
- **PIC depended on the host compiler's default for deps.** bun's own
objects were `-fno-pic`, vendored deps got whatever the building clang
defaults to. CI's clang defaults to non-PIE so release artifacts were
unaffected, but on hosts whose clang defaults to PIE (Arch, Fedora,
Alpine, Homebrew) every dep was PIC: `.data.rel.ro` 541 KB instead of
109 KB and 4–7% more pages touched at startup. Every dep now gets bun's
PIC policy explicitly.
- **windows-arm64 tuned for Ampere.** `-mtune=ampere1` (copied from the
Linux server lane) padded every function and loop to 64 bytes on
Snapdragon hardware; MSVC, Chromium and Rust use generic tuning there.
Dropped; `-march=armv8-a+crc` unchanged.
- **Windows: the exe's import library overwrote the object archive.**
`bun.exe` exports symbols, so lld-link wrote `bun-profile.lib`, the same
path as the object archive `cpp-only` mode produces. It now goes to
`obj/<exe>.import.lib`.
- **Generated headers were one build late.** A generated header named
absolutely in a depfile didn't match its relative ninja output, so
includers recompiled on the *next* run (bun's `codegen/` headers too).
Fixed in `ninja.ts` as above.
- **FreeBSD/Android shipped 13 MB of ICU data they never load.** Only
the Linux and Windows prebuilts filtered and compressed ICU data; every
non-macOS target now does.
- **With a warm ccache, the second build of a fresh build dir recompiled
hundreds of objects (macOS, Windows).** The build exported
`CCACHE_FILECLONE=1`; entries stored that way are raw files, and a hit
is materialized by clone (APFS) or CopyFile (Windows), both keeping the
entry's mtime, so objects came out older than headers generated in the
same run. Dropped, plus `CCACHE_NAMESPACE=bun` so the raw entries
already in everyone's cache are never hit again.
- **`bun run build` never reached a no-op with an isolated-layout
`node_modules`.** The install edge declared
`node_modules/<dep>/package.json` as outputs; ninja pre-creates output
directories, so `node_modules/<dep>/` existed before `bun install` ran,
bun's isolated linker skipped the symlink, and install (plus the
esbuild/cargo edges behind it) re-ran on every build. It now declares
the `node_modules/<dep>` entry itself.
- **Links were serialized through ninja's console pool.** `link` was a
`pool = console` rule (depth 1), so once the graph had more than one
executable (bun, testFFI, JSC's LLInt extractors) bun's link waited
behind the others — ~25 s per release lane. Links are ordinary edges
now; the smoke test and ClassInfo check became ninja validations of the
link.
- **Every build after a build-script edit configured twice.** ninja
judges its `regen` edge by the mtime it recorded for `build.ninja`, not
the file's, so the manifest build.ts had just refreshed still looked
stale and ninja ran configure again (`[0/1] reconfigure`). Configure now
stamps the manifest and `ninja -t restat`s it.
- **bun.exe exported bmalloc's API and libpas' `g_config`.** bmalloc's
`BEXPORT` is `__declspec(dllexport)` even in a static build (WTF's macro
has the fork's carve-out, bmalloc's doesn't); 23 stray exports on top of
the intended Node-API/V8/libuv/llhttp set (same on main's prebuilt).
Found by the new export check; fixed with `-DBEXPORT=`.
- **Debug builds ran ~93 static initializers from the generated
classes.** `ZigGeneratedClasses.cpp` initialized each `extern "C"
<Type>__ptrOffset` from a non-`constexpr` `offsetOfWrapped()`; `-O2`
folded them, `-O0` ran them at startup. `constexpr` now, so they're
constant-initialized in every build (found by the new initializer
audit).
- **bun.exe ran in the Windows Vista compatibility context.** Its
manifest had no `<compatibility>`/`<trustInfo>` section, so Windows
applied Vista-era behavior (version APIs capped at 6.2, PCA monitoring)
to bun and every addon in-process. Now declares Windows 7–11 and
`asInvoker`, like node.exe; one visible effect is `process.report`'s
`header.osRelease` reporting `10.0` instead of `6.1` on Windows 10/11
(`os.release()` was already right, it uses `RtlGetVersion`). Found by
comparing against node's binaries.
- **Linux/FreeBSD exported four bun-internal `napi_internal_*` helpers**
through the `napi*` glob in the version script (macOS/Windows didn't).
Renamed out of the `napi_` namespace.
- **WebKit's own warning set wasn't applied when compiling it** (once
JSC is built here rather than by cmake): `-Wall -Wextra …
-Werror=undefined-inline/-internal` and the `-Wno-*` upstream carries
(e.g. clang 21's `-Wcharacter-conversion`) now match
WebKitCompilerFlags.cmake / OptionsMSVC.cmake.

### Problem
- `npm install` fails in the repo root with `npm error code
EUNSUPPORTEDPROTOCOL` and `Unsupported URL Type "workspace:"`. The
`workspace:` protocol came from `packages/@types/bun`, a one-line alias
of the DefinitelyTyped package whose only job was to let tsc resolve the
type reference `bun` to the checkout's `packages/bun-types`.
- The build installs three package.json files with bun (the repo root,
`packages/bun-error`, `src/node-fallbacks`). A machine without bun
cannot run those steps (#6887).

### Fix
- Remove `packages/@types/bun`, its workspace entry, its devDependency,
and its `resolutions` entry. The four tsconfigs that reached it (`src`,
`src/js`, `src/codegen/bindgenv2`, `scripts/build`) now list
`packages/bun-types` in `types`, as `test/tsconfig.json` already does.
- Pin the root devDependencies to the versions in `bun.lock`.
- Add `--package-manager=npm`. Each install then runs
`scripts/build/npm-ci.ts`: it writes `package-lock.json` from that
directory's `bun.lock`, runs `npm ci` and `npm rebuild`, and deletes the
file again. The default stays bun.
- Verified: for the root, the translated lockfile is byte-identical to
what `npm install --package-lock-only` writes. The codegen output is
identical with both package managers, on Linux and on Windows, and no
lockfile is left behind. tsc error counts are unchanged, and the
bun-types integration test passes.

### Background
- The root install provides esbuild and lezer for codegen.
- npm reads the lockfile only from the directory of `package.json`, so
the translated file lives there for the duration of `npm ci`.
`.gitignore` already ignores `package-lock.json`.
- This PR is one part of #34876, split out for review, with #41222,
#41223, and #41224.

<details><summary>Notes</summary>

- `npm-ci.ts` reads only built-ins, so it runs under bun or node (the

JavaScriptCore, WTF, bmalloc — and, on every target except macOS, ICU —
are compiled from source inside bun's own ninja graph, like every other
vendored dependency, instead of being downloaded as a prebuilt
`bun-webkit-*` tarball. This is the default for every build, local and
CI; `--webkit=prebuilt` remains as an explicit opt-in.

### What changes

**CI**
- All 13 `build-bun` lanes (Linux x64/arm64 glibc + baseline + musl +
ASAN, Android, FreeBSD, macOS x64/arm64, Windows x64/arm64) compile JSC
in the same graph as bun's own C++; no
`libJavaScriptCore.a`/`libWTF.a`/`libbmalloc.a` step — the objects go
straight into the same archive/link as bun's.
- A WebKit change no longer needs a prebuilt to be published before bun
can build against it: bump `WEBKIT_VERSION` to any commit pushed to
oven-sh/WebKit.
- `build-bun` steps take ~1–2.5 min longer per target. Binary sizes: see
the table below (nothing grew; FreeBSD/Android −13 MB from ICU data
packing, windows-arm64 −3.5 MB, the rest under 2 MB).
- Build images: `bootstrap.sh` v42 adds `flex`/`bison` (host `migcom`
for the macOS lanes). Linux images are baked as a Buildkite job on a
fresh machine of the target distro plus a `wait-for-image` step, instead
of an instance driven over SSH from the hosted agent.
- `build-bun` is a plain full build now (the `archive-link` mode is
removed): bun's objects go straight into the link as in a local build,
and the per-lane `libbun-*.a.gz` / `libbun_runtime.a.gz` / dep-lib
artifact uploads, which nothing consumed, are gone. `cpp-only` keeps its
archive for the split pipeline. The precompiled header is built whenever
C++ is compiled (previously skipped for CI + full).
- `bootstrap.ps1` v23: ruby and zstd for native from-source builds on
the Windows images, and LLVM 21.1.8 installed from its release installer
(scoop's `llvm@21.1.8` now generates a non-existent `.msi` URL).
- Buildkite canvas: `verify-baseline` and `trace-order` are drawn beside
each target's build group instead of inside it (from #41408; no
scheduling change).

**Local development**
- `bun bd` / `bun run build` compile JSC too (fetched by ninja like
every dep, ~35 MB sparse; the first build of a build dir pays ~2 min for
JSC, then it is incremental and ccache-friendly). Host tools needed:
`ruby`, `python3`, `perl` (JSC's generators), `zstd` (ICU data,
non-macOS targets), and `flex`/`bison` only when cross-compiling a macOS
target from Linux (a Mac uses Xcode's `mig`).
- Release builds are LTO by default everywhere (what CI ships);
`--lto=off` for fast relinks. The `btg` profile is gone (it was "release
+ LTO"). On a native macOS or Windows host whose rustc LLVM is newer
than clang's (today: nightly LLVM 22 vs Homebrew llvm@21), the Rust↔C++
cross-language step is skipped and each half LTOs on its own — Apple's
ld runs LTO through clang's libLTO, which can't read newer bitcode and
has no lld to swap in; CI cross-compiles both from Linux with rustc's

- Working on JSC itself: `--local-deps=WebKit=<your clone>` on any

- Upgrading WebKit: the build itself checks the fetched tree against

### How it works

- **One dep kind.** Every C/C++ dep is a `direct` spec in
`scripts/build/deps/*.ts`: source groups (each with its own
flags/includes/PCH), `steps` (generators, host tools, target
executables), `headers` (files written at configure). WebKit is the same
shape as zlib, just larger; the `custom` kind is gone.
- **WebKit** (`deps/webkit.ts` +
`deps/webkit-{bmalloc,wtf,jsc,llint,inspector}-sources.ts`): bmalloc,
WTF and JavaScriptCore as three source groups; JSC's TUs are the unified
bundles listed explicitly in `webkit-sources.ts` (as WebKit's bundler
forms them, regenerated on a bump) plus the `@no-unify` files; every
generator WebKit's cmake runs (create_hash_table LUTs,
bytecode/Air/yarr/wasm generators, JS builtins, inspector protocol,
GeneratePreferences, offlineasm via the two LLInt extractor executables,
MIG on macOS) is a step invoking the same script with the same
arguments; `cmakeconfig.h`, the `<JavaScriptCore/X.h>` / `<bmalloc/X.h>`
forwarding stubs and the bundle files are `headers` entries. Compile
flags reproduce OptionsJSCOnly / WebKitCompilerFlags / OptionsMSVC per
platform on top of bun's dep-global flags, so JSC gets bun's `-march`,
LTO, sanitizer and hardening settings. Nothing reads the WebKit tree at
configure time.
- **ICU** (`deps/icu.ts` + `deps/icu-sources.ts`, `icu-data.ts`):
`common`/`i18n` compiled in-graph; a host `icupkg`; the data file
filtered and its display-name items zstd-repacked with a trained
dictionary, decompressed on first use through
`src/jsc/bindings/bun_icu_decompress.cpp`. That scheme was already in
the Linux/Windows prebuilts; it now applies uniformly (Linux, musl,
Android, FreeBSD, Windows). macOS keeps the SDK's `libicucore`.
- **Link-time checks** run as ninja validations of bun's link on every
lane, all static (`scripts/build/verify-binary.ts`, expectations per
target in `binary-expectations.ts`): exported symbols vs the lists in
`src/`; the exact NEEDED / dylib / import-DLL set and the glibc (2.17) /
FBSD (1.7) symbol-version ceiling (un-numbered version nodes such as
`GLIBC_ABI_DT_RELR` count; Android's floor is bionic's `LIBC`…`LIBC_P` /
`LIBLOG`…`LIBLOG_O`, API 28); forbidden imports (`__cxa_throw`,
`__emutls_*`, …); every static initializer symbolized and matched
against the runtime's known ones (none may come from bun/JSC/WTF);
nx-stack / no-RWX / PIE / DllCharacteristics; debug-info shape; and no
symbol strongly defined by two link inputs (every input must be readable
by the scanning tool — under the rustc/clang LLVM skew the scan uses
rustup's `llvm-nm`, hence the `llvm-tools` component in
`rust-toolchain.toml`). Plus the existing `--revision` smoke test
(host-runnable targets only) and the JSC ClassInfo audit.
- **testFFI** (JSC's bun:ffi ABI test program) is compiled and linked by
`bun.ts` next to `bun` from the same objects and shipped in the CI
artifact; the test fails, not skips, if it is missing in CI.
- **Native macOS and Windows hosts** (which CI never exercises — every
lane cross-compiles from Linux) were built end to end: Xcode's `mig`,
clang-cl as the target compiler with clang as the host compiler, ICU
data packing and testFFI all work there.
- **Cross targets** build from the Linux agents as before: macOS with
the SDK plus Apple's `migcom` built for the host
(`deps/bootstrap-cmds.ts`), Windows with clang-cl and the auto-fetched
MSVC sysroot, FreeBSD/Android with their sysroots. macOS and Windows
hosts work too.
- **Linking without archives.** bun's own objects and the dependencies'
objects go straight to the link; no `libbun-*.a`, no per-dep
`.a`/`.lib`. The dep objects are a lazy group (`link()`'s `lazyObjects`:
lld's `/start-lib … /end-lib`, i.e. taken only if referenced — a static
library's semantics minus the file). That matters on Windows: COFF
linkers discard unreferenced code only at COMDAT granularity, so an
object with plain sections that nothing calls (any NASM output —
BoringSSL's AES-GCM-SIV asm is never called on Windows by BoringSSL's
own design) would otherwise be linked whole; upstream and Chromium rely
on archive member selection for the same thing. The group reaches
lld-link through clang-cl as `/clang:-Wl,@<exe>.lazy.rsp`. On ELF/Mach-O
the objects simply follow bun's in `$in` (those linkers dead-strip per
section).
- **Windows: `/lld-allow-duplicate-weak`.** WTF/JSC reference bun's
hooks (`WTFTimer__*`, `Bun__errorInstance__finalize`,
`Bun__reportUnhandledError`) as `__attribute__((weak))`; COFF has no
weak undefined symbol, so each referencing TU carries a weak external
with its own absolute-0 default and lld-link (MSVC mode) reports two
such TUs as a duplicate symbol even though bun's strong definition wins
— which ThinLTO importing `RunLoop::TimerBase::start()` into a JSC
module produces. lld-link's switch for exactly that check is on for
bun's and the JSC test programs' links (the latter previously used
`/force:multiple`); duplicate *strong* definitions still error. It
becomes a no-op once lld-link accepts several weak references to one
symbol (fixed in bun's LLVM toolchain) and is to be dropped then.

Build-system changes that came along:
- `ninja.ts` declares every build-dir output under its absolute path as
well, so a header a compiler depfile names absolutely resolves to its
generator and its includers recompile in the same run (was one build
late; affected bun's own `codegen/` too).
- `ninja_required_version` is 1.11 (validations). One phony per
order-only group instead of repeating generated-header lists on every
compile edge.
- One `dep_codegen` rule (`stream.ts --cwd/--env/--stdout`) for all dep
generators; `host_cc`/`host_cxx`/`host_link` for host tools;
`hostCc`/`hostCxx` are the plain clang drivers for any Windows target;
`-fsanitize=address` is part of the target link flags; tarball sources
carry a `sha256`; dep fetches print `[name] … (elapsed)`.
- Tools that assumed a prebuilt layout now read the build:
`scripts/jsc-exception-lint` takes JSC's TUs from
`compile_commands.json`; `bun-inspector-protocol`'s generator reads our
`CombinedDomains.json`; `.vscode/c_cpp_properties.json` just points at
the compile database.

### Bugs and misconfigurations on main that this fixes

Found by diffing compile lines against WebKit's cmake and dissecting
main's release binaries target by target:

- **windows-arm64: JSC compiled with FP contraction.** JSC's CMakeLists
sets `-ffp-contract=off -fno-slp-vectorize` for the whole target;
clang-cl ignores the GNU spellings and cmake's probe dropped them, so
the Windows prebuilt never had them. On arm64 that fused `Date`
arithmetic (`setNewValueFromTimeArgs`, `millisecondsFromComponents`,
`dateProtoFuncSetYear`, …) into `fmadd`, i.e. different rounding than
every other platform and than the JIT. Now passed as
`/clang:-ffp-contract=off /clang:-fno-slp-vectorize`.
- **Stack protector depended on the host compiler's vendor default.**
Nothing stated a policy, so CI (apt.llvm.org clang) shipped without it
while a build on Arch/Alpine/Fedora-packaged clang got
`-fstack-protector-strong` in every eligible function (62k canary checks
vs 161), and the musl JSC prebuilt (Alpine clang) had it while no other
target did. `-fno-stack-protector` is now explicit on unix.
- **PIC depended on the host compiler's default for deps.** bun's own
objects were `-fno-pic`, vendored deps got whatever the building clang
defaults to. CI's clang defaults to non-PIE so release artifacts were
unaffected, but on hosts whose clang defaults to PIE (Arch, Fedora,
Alpine, Homebrew) every dep was PIC: `.data.rel.ro` 541 KB instead of
109 KB and 4–7% more pages touched at startup. Every dep now gets bun's
PIC policy explicitly.
- **windows-arm64 tuned for Ampere.** `-mtune=ampere1` (copied from the
Linux server lane) padded every function and loop to 64 bytes on
Snapdragon hardware; MSVC, Chromium and Rust use generic tuning there.
Dropped; `-march=armv8-a+crc` unchanged.
- **Windows: the exe's import library overwrote the object archive.**
`bun.exe` exports symbols, so lld-link wrote `bun-profile.lib`, the same
path as the object archive `cpp-only` mode produces. It now goes to
`obj/<exe>.import.lib`.
- **Generated headers were one build late.** A generated header named
absolutely in a depfile didn't match its relative ninja output, so
includers recompiled on the *next* run (bun's `codegen/` headers too).
Fixed in `ninja.ts` as above.
- **FreeBSD/Android shipped 13 MB of ICU data they never load.** Only
the Linux and Windows prebuilts filtered and compressed ICU data; every
non-macOS target now does.
- **With a warm ccache, the second build of a fresh build dir recompiled
hundreds of objects (macOS, Windows).** The build exported
`CCACHE_FILECLONE=1`; entries stored that way are raw files, and a hit
is materialized by clone (APFS) or CopyFile (Windows), both keeping the
entry's mtime, so objects came out older than headers generated in the
same run. Dropped, plus `CCACHE_NAMESPACE=bun` so the raw entries
already in everyone's cache are never hit again.
- **`bun run build` never reached a no-op with an isolated-layout
`node_modules`.** The install edge declared
`node_modules/<dep>/package.json` as outputs; ninja pre-creates output
directories, so `node_modules/<dep>/` existed before `bun install` ran,
bun's isolated linker skipped the symlink, and install (plus the
esbuild/cargo edges behind it) re-ran on every build. It now declares
the `node_modules/<dep>` entry itself.
- **Links were serialized through ninja's console pool.** `link` was a
`pool = console` rule (depth 1), so once the graph had more than one
executable (bun, testFFI, JSC's LLInt extractors) bun's link waited
behind the others — ~25 s per release lane. Links are ordinary edges
now; the smoke test and ClassInfo check became ninja validations of the
link.
- **Every build after a build-script edit configured twice.** ninja
judges its `regen` edge by the mtime it recorded for `build.ninja`, not
the file's, so the manifest build.ts had just refreshed still looked
stale and ninja ran configure again (`[0/1] reconfigure`). Configure now
stamps the manifest and `ninja -t restat`s it.
- **bun.exe exported bmalloc's API and libpas' `g_config`.** bmalloc's
`BEXPORT` is `__declspec(dllexport)` even in a static build (WTF's macro
has the fork's carve-out, bmalloc's doesn't); 23 stray exports on top of
the intended Node-API/V8/libuv/llhttp set (same on main's prebuilt).
Found by the new export check; fixed with `-DBEXPORT=`.
- **Debug builds ran ~93 static initializers from the generated
classes.** `ZigGeneratedClasses.cpp` initialized each `extern "C"
<Type>__ptrOffset` from a non-`constexpr` `offsetOfWrapped()`; `-O2`
folded them, `-O0` ran them at startup. `constexpr` now, so they're
constant-initialized in every build (found by the new initializer
audit).
- **bun.exe ran in the Windows Vista compatibility context.** Its
manifest had no `<compatibility>`/`<trustInfo>` section, so Windows
applied Vista-era behavior (version APIs capped at 6.2, PCA monitoring)
to bun and every addon in-process. Now declares Windows 7–11 and
`asInvoker`, like node.exe; one visible effect is `process.report`'s
`header.osRelease` reporting `10.0` instead of `6.1` on Windows 10/11
(`os.release()` was already right, it uses `RtlGetVersion`). Found by
comparing against node's binaries.
- **Linux/FreeBSD exported four bun-internal `napi_internal_*` helpers**
through the `napi*` glob in the version script (macOS/Windows didn't).
Renamed out of the `napi_` namespace.
- **WebKit's own warning set wasn't applied when compiling it** (once
JSC is built here rather than by cmake): `-Wall -Wextra …
-Werror=undefined-inline/-internal` and the `-Wno-*` upstream carries
(e.g. clang 21's `-Wcharacter-conversion`) now match
WebKitCompilerFlags.cmake / OptionsMSVC.cmake.

## What

A hardening and robustness pass across the runtime: input validation,
bounds checking, protocol-state handling, and object-lifetime
correctness in ~200 files. It contains 122 individual fixes and ~190 new
tests (171 new `test`/`it` blocks, several parameterized, across 79
existing test files). No new API is introduced; every behavioral change
below has a test unless explicitly noted, and each is aligned with Node,
the relevant RFC/spec, or the upstream reference implementation.

## Potentially breaking / behavior-visible changes

Read this section first. Everything else in the PR preserves behavior
for valid inputs.

- **`Bun.serve` `request.url` is only synthesized from a structurally
valid `Host`.** For every HTTP/1.x request (`Bun.serve` and node-compat
servers alike), a `Host` value that is empty or contains bytes outside
`uri-host [":" port]` (RFC 3986 authority: alphanumerics, `.-:_~%[]` and
sub-delims) is never used as the authority of the synthesized
`request.url`; `request.url` falls back to the request target (e.g.
`/path`) and the request is still served. No request is rejected on the
basis of the `Host` field value, and a valid `Host` still round-trips
into `request.url` exactly. Why: `request.url` should never carry an
authority that cannot come back out of `new URL()`.
- **`fetch` rejects request lines it cannot legally serialize.** A URL
path/host (or, for proxied requests, the full href) containing a control
character, space, or DEL now fails with `InvalidURL` before any bytes
are written (RFC 9112 request-line grammar; normal `fetch()` input is
percent-encoded by the URL parser and unaffected). Also: a redirect
whose `Location` resolves to a non-http(s) scheme now fails with
`UnsupportedRedirectProtocol` (Fetch spec, matches undici); a `101`
arriving on the pre-tunnel leg of a proxied request is treated as an
unrequested upgrade; connections whose identity was accepted by a
per-request `checkServerIdentity` callback are never entered into or
taken from the keep-alive pool.
- **An own `__proto__` key from data files and macros is printed as a
computed key.** The `json`, `jsonc`, `json5`, `toml`, `yaml`, and
CSS-module loaders — and objects returned from Bun macros — now emit
`["__proto__"]: ...` so importing such data yields an own `__proto__`
property (like `JSON.parse`) instead of a prototype assignment. Who
notices: only code importing data with a `__proto__` key; matches
esbuild's JSON loader and Node semantics.
- **`node:url` legacy `url.parse` lookup tables no longer inherit from
`Object.prototype`** (both `node:url` and the browser fallback), the
hostless/slashed lookups use the lowercased protocol, and `url.parse(s,
true).query` is a null-prototype object (empty query included). All
three match Node's `lib/url.js` exactly. Who notices: code doing
`query.hasOwnProperty(...)` or parsing schemes named like `toString:`.
- **WebSocket client: missing negotiated subprotocol fails the
handshake.** Per RFC 6455 §4.1, if `new WebSocket(url, ["a"])` requested
subprotocols and the server's 101 omits `Sec-WebSocket-Protocol`, the
connection now closes with 1002 instead of opening with `ws.protocol ===
""`. Matches browsers, `ws`, and undici. Connections that request no
subprotocol are unaffected.
- **HTTP/2 (client and server) enforces RFC 9113 message framing.**
Trailer blocks must carry END_STREAM and no pseudo-headers;
`content-length` must be `1*DIGIT`, non-duplicated, and equal to the
DATA actually received (CONNECT exempt) — violations get
RST_STREAM(PROTOCOL_ERROR) instead of being delivered. With
`maxSessionMemory` exceeded, new peer streams are refused with
REFUSED_STREAM (retryable), and reset streams promptly release their
native state — Node/nghttp2 parity throughout. The all-streams teardown
helper now throws a `TypeError` for a non-numeric error code instead of
coercing it per stream.
- **`node:http2` HTTP/1 fallback (`allowHTTP1`) frames responses like
Node.** Header-name matching is case-insensitive; HEAD and
close-delimited responses don't get an auto `Transfer-Encoding:
chunked`/terminating chunk; `writeHead` now throws
`ERR_HTTP_INVALID_STATUS_CODE` / `ERR_INVALID_CHAR` like Node's
`ServerResponse`. Re-entrant `sendTrailers()` raises
`ERR_HTTP2_TRAILERS_ALREADY_SENT` in the same order Node does.
- **`node:http(s)` proxy `CONNECT` endpoint is validated with
`validateHeaderValue` in release builds** (previously a debug-only
assertion), so an invalid host/port surfaces as the same error Node
throws.
- **Glob: walking through a self-referential directory symlink
completes.** With `followSymlinks`, a link that resolves to one of its
own live ancestors is descended exactly once (like `find -L`, glibc
`fts`, node-glob); sibling/cousin links to the same target are still all
visited. One pre-existing test changed: it previously asserted the walk
failed with `ENAMETOOLONG` after the path grew past the limit; it now
asserts the scan completes.
- **Resolver: an `exports`/`imports` target whose expansion would exceed
the OS path limit is a normal resolution error** (`Invalid module
specifier` / `Invalid package target`, as Node models it) instead of a
hard failure.
- **Shell:** template arrays nested deeper than 100 levels throw a clear
error instead of recursing without bound; an interpolated string equal
to `if`/`then`/`elif`/`else`/`fi` is treated as data, never as a
reserved word (POSIX: reserved words are only recognized literally);
`$.escape` now quotes strings containing tab, CR, or `?` (word
delimiters / glob metacharacters).
- **`bun pack` / `bun publish` include/exclude matches npm-packlist.**
With a `"files"` field, the non-overridable defaults (`.git`, `.npmrc`,
`node_modules`, lockfiles) are now applied inside the `files` traversal
too; conversely `.hg` moved to the *overridable* default-ignore list, so
`"files"` can re-include it — exactly npm's split.
- **`bun upgrade` verifies the downloaded artifact against the digest
the GitHub Releases API reports** for that asset, and fails with a
retryable error on mismatch. If the API reports no (or an unrecognized)
digest, behavior is unchanged.
- **install:** an `integrity` string carrying several space-separated
digests (legal SSRI) is now parsed correctly and verified against the
strongest algorithm present (see Deviations); a stored `bun.lockb` with
a non-0/1 byte in a boolean slot fails validation instead of being
reinterpreted; lifecycle scripts for *registry* packages always come
from the installed `package.json` (never from lockfile bytes), matching
what Bun writes and what npm does; isolated installs apply the same
name/alias shape validation as hoisted installs; bin links reached
through a subdirectory get the same resolved-containment check the
dotted forms already had (npm only links files inside the package
folder).
- **`node:fs`:** `mode` arguments are no longer masked to `0o777`
(setuid/setgid/sticky pass through to the syscall, like Node);
`copyFile`/`cp` create the destination with the source's permission bits
(libuv parity); on Windows, `cp` copies directory junctions/symlinks via
the unprivileged-create + junction-fallback helpers and rewrites
`\\?\UNC\` targets to `\\server\share` form (libuv parity), so copying a
tree with junctions works without elevation; on macOS the
`clonefile`/`openat` paths use `NOFOLLOW` so the copy matches the
`lstat` classification (`dereference:false`).
- **Web plumbing observable from JS:** record conversion (`new
Headers(obj)`, fetch init, `URLSearchParams`, …) snapshots the key list
once and re-resolves keys mutated by a converter, exactly as Web IDL
specifies (deleted keys skipped, replaced values re-read) — released
Bun/Node/WebKit order preserved; `TextDecoder.decode` over a
`SharedArrayBuffer` or resizable buffer view snapshots the bytes first;
consuming a `Blob`/`Response` body no longer empties *other* objects
sharing the same byte store (transfer only when sole owner); deeply
nested serialized arrays in `structuredClone` data hit the same
recursion cap objects already had; the SIMD `decodeURIComponent` fast
path decodes non-ASCII input as UTF-8 (with U+FFFD for ill-formed
sequences) instead of throwing/garbling.
- **N-API / V8 API:** `napi_create_arraybuffer` returns zeroed memory
(Node contract); `napi_get_typedarray_info`/`napi_get_dataview_info`
report the view's real `byte_offset`; `v8::String::Utf8Length` returns
the exact byte count `WriteUtf8` will produce for ill-formed UTF-16;
`v8::Number::New` canonicalizes NaN payloads.
- **Dev-only endpoints check `Host`/`Origin`:** the inspector (`bun
--inspect`) HTTP/WebSocket endpoint applies its Host/Origin checks
before the `/json`* discovery routes and rejects non-matching DNS-name
`Host` values with 400 (Node inspector semantics); the bake/dev-server
internal routes require an allowed Host and same-origin for the
error-report/sourcemap endpoints; internal HMR pub/sub topics are
namespaced so user `publish`/`subscribe` topic strings can never collide
with them.
- **markdown:** reference-link expansion is charged against md4c's exact
output budget (`16 × min(input, 64 KiB)` scale); once exhausted, further
references degrade to literal bracketed text — no error — exactly as
md4c does.
- **Misc small behavior corrections:** `checkPrime` validates the
candidate before the options (Node's order); HKDF rejects non-secret
`KeyObject`s with `ERR_CRYPTO_INVALID_KEY_OBJECT_TYPE` (current Node);
Ed25519 sign/verify with a wrong-length key errors/returns false; X25519
JWK import honors `kty`/`crv`/`use`/`key_ops`/`ext`; SPKAC helpers
return false/empty for empty or whitespace-only input (Node);
`CookieMap.delete` of a `__Host-`/`__Secure-` cookie emits `Secure` so
browsers accept the expiry; postgres `escapeIdentifier` rejects embedded
NUL (`pg` parity); valkey/redis pending commands reject with "Connection
closed" on disconnect and out-of-band push frames never consume an
unrelated command's promise (RESP3); semver strings consisting only of
`v`/`=`/whitespace parse as `*` (node-semver); `Bun.wrapAnsi` measures
rows whose seam joins grapheme clusters (combining marks/ZWJ/VS16) the
way npm `wrap-ansi` does; bash/zsh completions handle script names
containing `:` and other special characters; the Docker images verify
(not just decode) the release checksum signature.

## Deviations / decisions

- **Integrity: strongest-single-digest verification.** When an
`integrity` field carries several digests, Bun verifies the strongest
supported algorithm present; when several digests of that same algorithm
are present, the first is the one verified. npm/ssri accepts a match on
*any* digest of the chosen algorithm — keeping the full set needs
plumbing through the manifest cache/lockfile types and is left for a
follow-up.
- **No response-decompression size cap in `fetch`.** A per-response
decompressed-body limit was implemented and then deliberately removed
from this PR ("Keep fetch response decompression unbounded"): Node
imposes none, and any cap is a behavior change for legitimate large
responses. The net diff has no decompression change.
- **markdown reference expansion degrades instead of erroring**,
matching md4c exactly (see highlights). No error is ever surfaced.
- **Record conversion keeps the specification's per-property order** —
`[[GetOwnProperty]]`/`Get` interleaved with value conversion, so a
`toString` that mutates a sibling property is observed and a deleted one
skipped, the same as released Bun, Node, and WebKit. The property table
is never held across user code.
- Dead code removed because these changes made it unreachable:
`cache::Entry.external_free_function` (plus `Entry::new` and the free
branch of `Entry::deinit`) and `AlreadyBundled::bytecode_slice`; the
`bun_wyhash` dependency of `sql_jsc` is dropped.
- Deeper, behavior-visible sibling work in the same areas was split into
its own PRs so it can be reviewed on its own terms: #33054 (`node:https`
TLS option set), #33055 (websocket dispatch re-entrancy), #33056
(FileSystemRouter/resolver entry locking), #33060 (`child_process`
uid/gid), #33061 (`node:http` server headers/request timeouts). Nothing
from those PRs is claimed here.
- The changes to CI workflow files, shell completion scripts,
Dockerfiles, and the VS Code extension have no automated-test harness; a
few lifetime/ordering corrections have no deterministic observation from
JS (they are covered by the existing suites and the sanitizer jobs) and
are noted as such instead of shipping a non-asserting test.

A hardening and robustness pass across the runtime: input validation,

## Potentially breaking / behavior-visible changes

Read this section first. Everything else in the PR preserves behavior
for valid inputs.

- **`Bun.serve` `request.url` is only synthesized from a structurally
valid `Host`.** For every HTTP/1.x request (`Bun.serve` and node-compat
servers alike), a `Host` value that is empty or contains bytes outside
`uri-host [":" port]` (RFC 3986 authority: alphanumerics, `.-:_~%[]` and
sub-delims) is never used as the authority of the synthesized
`request.url`; `request.url` falls back to the request target (e.g.
`/path`) and the request is still served. No request is rejected on the
basis of the `Host` field value, and a valid `Host` still round-trips
into `request.url` exactly. Why: `request.url` should never carry an
authority that cannot come back out of `new URL()`.
- **`fetch` rejects request lines it cannot legally serialize.** A URL
path/host (or, for proxied requests, the full href) containing a control
character, space, or DEL now fails with `InvalidURL` before any bytes
are written (RFC 9112 request-line grammar; normal `fetch()` input is
percent-encoded by the URL parser and unaffected). Also: a redirect
whose `Location` resolves to a non-http(s) scheme now fails with
`UnsupportedRedirectProtocol` (Fetch spec, matches undici); a `101`
arriving on the pre-tunnel leg of a proxied request is treated as an
unrequested upgrade; connections whose identity was accepted by a
per-request `checkServerIdentity` callback are never entered into or
taken from the keep-alive pool.
- **An own `__proto__` key from data files and macros is printed as a
computed key.** The `json`, `jsonc`, `json5`, `toml`, `yaml`, and
CSS-module loaders — and objects returned from Bun macros — now emit
`["__proto__"]: ...` so importing such data yields an own `__proto__`
property (like `JSON.parse`) instead of a prototype assignment. Who
notices: only code importing data with a `__proto__` key; matches
esbuild's JSON loader and Node semantics.
- **`node:url` legacy `url.parse` lookup tables no longer inherit from
`Object.prototype`** (both `node:url` and the browser fallback), the
hostless/slashed lookups use the lowercased protocol, and `url.parse(s,
true).query` is a null-prototype object (empty query included). All
three match Node's `lib/url.js` exactly. Who notices: code doing
`query.hasOwnProperty(...)` or parsing schemes named like `toString:`.
- **WebSocket client: missing negotiated subprotocol fails the
handshake.** Per RFC 6455 §4.1, if `new WebSocket(url, ["a"])` requested
subprotocols and the server's 101 omits `Sec-WebSocket-Protocol`, the
connection now closes with 1002 instead of opening with `ws.protocol ===
""`. Matches browsers, `ws`, and undici. Connections that request no
subprotocol are unaffected.
- **HTTP/2 (client and server) enforces RFC 9113 message framing.**
Trailer blocks must carry END_STREAM and no pseudo-headers;
`content-length` must be `1*DIGIT`, non-duplicated, and equal to the
DATA actually received (CONNECT exempt) — violations get
RST_STREAM(PROTOCOL_ERROR) instead of being delivered. With
`maxSessionMemory` exceeded, new peer streams are refused with
REFUSED_STREAM (retryable), and reset streams promptly release their
native state — Node/nghttp2 parity throughout. The all-streams teardown
helper now throws a `TypeError` for a non-numeric error code instead of
coercing it per stream.
- **`node:http2` HTTP/1 fallback (`allowHTTP1`) frames responses like
Node.** Header-name matching is case-insensitive; HEAD and
close-delimited responses don't get an auto `Transfer-Encoding:
chunked`/terminating chunk; `writeHead` now throws
`ERR_HTTP_INVALID_STATUS_CODE` / `ERR_INVALID_CHAR` like Node's
`ServerResponse`. Re-entrant `sendTrailers()` raises
`ERR_HTTP2_TRAILERS_ALREADY_SENT` in the same order Node does.
- **`node:http(s)` proxy `CONNECT` endpoint is validated with
`validateHeaderValue` in release builds** (previously a debug-only
assertion), so an invalid host/port surfaces as the same error Node
throws.
- **Glob: walking through a self-referential directory symlink
completes.** With `followSymlinks`, a link that resolves to one of its
own live ancestors is descended exactly once (like `find -L`, glibc
`fts`, node-glob); sibling/cousin links to the same target are still all
visited. One pre-existing test changed: it previously asserted the walk
failed with `ENAMETOOLONG` after the path grew past the limit; it now
asserts the scan completes.
- **Resolver: an `exports`/`imports` target whose expansion would exceed
the OS path limit is a normal resolution error** (`Invalid module
specifier` / `Invalid package target`, as Node models it) instead of a
hard failure.
- **Shell:** template arrays nested deeper than 100 levels throw a clear
error instead of recursing without bound; an interpolated string equal
to `if`/`then`/`elif`/`else`/`fi` is treated as data, never as a

## Deviations / decisions

- **Integrity: strongest-single-digest verification.** When an
`integrity` field carries several digests, Bun verifies the strongest
supported algorithm present; when several digests of that same algorithm
are present, the first is the one verified. npm/ssri accepts a match on
*any* digest of the chosen algorithm — keeping the full set needs
plumbing through the manifest cache/lockfile types and is left for a
follow-up.
- **No response-decompression size cap in `fetch`.** A per-response
decompressed-body limit was implemented and then deliberately removed
from this PR ("Keep fetch response decompression unbounded"): Node
imposes none, and any cap is a behavior change for legitimate large
responses. The net diff has no decompression change.
- **markdown reference expansion degrades instead of erroring**,
matching md4c exactly (see highlights). No error is ever surfaced.
- **Record conversion keeps the specification's per-property order** —
`[[GetOwnProperty]]`/`Get` interleaved with value conversion, so a
`toString` that mutates a sibling property is observed and a deleted one
skipped, the same as released Bun, Node, and WebKit. The property table
is never held across user code.
- Dead code removed because these changes made it unreachable:
`cache::Entry.external_free_function` (plus `Entry::new` and the free
branch of `Entry::deinit`) and `AlreadyBundled::bytecode_slice`; the
`bun_wyhash` dependency of `sql_jsc` is dropped.
- Deeper, behavior-visible sibling work in the same areas was split into
its own PRs so it can be reviewed on its own terms: #33054 (`node:https`
TLS option set), #33055 (websocket dispatch re-entrancy), #33056
(FileSystemRouter/resolver entry locking), #33060 (`child_process`
uid/gid), #33061 (`node:http` server headers/request timeouts). Nothing
from those PRs is claimed here.
- The changes to CI workflow files, shell completion scripts,
Dockerfiles, and the VS Code extension have no automated-test harness; a
few lifetime/ordering corrections have no deterministic observation from
JS (they are covered by the existing suites and the sanitizer jobs) and
are noted as such instead of shipping a non-asserting test.

### How it works

- **One dep kind.** Every C/C++ dep is a `direct` spec in
`scripts/build/deps/*.ts`: source groups (each with its own
flags/includes/PCH), `steps` (generators, host tools, target
executables), `headers` (files written at configure). WebKit is the same
shape as zlib, just larger; the `custom` kind is gone.

`deps/webkit-{bmalloc,wtf,jsc,llint,inspector}-sources.ts`): bmalloc,
WTF and JavaScriptCore as three source groups; JSC's TUs are the unified
bundles listed explicitly in `webkit-sources.ts` (as WebKit's bundler
forms them, regenerated on a bump) plus the `@no-unify` files; every
generator WebKit's cmake runs (create_hash_table LUTs,
bytecode/Air/yarr/wasm generators, JS builtins, inspector protocol,
GeneratePreferences, offlineasm via the two LLInt extractor executables,
MIG on macOS) is a step invoking the same script with the same
arguments; `cmakeconfig.h`, the `<JavaScriptCore/X.h>` / `<bmalloc/X.h>`
forwarding stubs and the bundle files are `headers` entries. Compile
flags reproduce OptionsJSCOnly / WebKitCompilerFlags / OptionsMSVC per
platform on top of bun's dep-global flags, so JSC gets bun's `-march`,
LTO, sanitizer and hardening settings. Nothing reads the WebKit tree at
configure time.
- **ICU** (`deps/icu.ts` + `deps/icu-sources.ts`, `icu-data.ts`):
`common`/`i18n` compiled in-graph; a host `icupkg`; the data file
filtered and its display-name items zstd-repacked with a trained
dictionary, decompressed on first use through
`src/jsc/bindings/bun_icu_decompress.cpp`. That scheme was already in
the Linux/Windows prebuilts; it now applies uniformly (Linux, musl,
Android, FreeBSD, Windows). macOS keeps the SDK's `libicucore`.
- **Link-time checks** run as ninja validations of bun's link on every
lane, all static (`scripts/build/verify-binary.ts`, expectations per
target in `binary-expectations.ts`): exported symbols vs the lists in
`src/`; the exact NEEDED / dylib / import-DLL set and the glibc (2.17) /
FBSD (1.7) symbol-version ceiling (un-numbered version nodes such as
`GLIBC_ABI_DT_RELR` count; Android's floor is bionic's `LIBC`…`LIBC_P` /
`LIBLOG`…`LIBLOG_O`, API 28); forbidden imports (`__cxa_throw`,
`__emutls_*`, …); every static initializer symbolized and matched
against the runtime's known ones (none may come from bun/JSC/WTF);
nx-stack / no-RWX / PIE / DllCharacteristics; debug-info shape; and no
symbol strongly defined by two link inputs (every input must be readable
by the scanning tool — under the rustc/clang LLVM skew the scan uses
rustup's `llvm-nm`, hence the `llvm-tools` component in
`rust-toolchain.toml`). Plus the existing `--revision` smoke test
(host-runnable targets only) and the JSC ClassInfo audit.
- **testFFI** (JSC's bun:ffi ABI test program) is compiled and linked by
`bun.ts` next to `bun` from the same objects and shipped in the CI
artifact; the test fails, not skips, if it is missing in CI.
- **Native macOS and Windows hosts** (which CI never exercises — every
lane cross-compiles from Linux) were built end to end: Xcode's `mig`,
clang-cl as the target compiler with clang as the host compiler, ICU
data packing and testFFI all work there.
- **Cross targets** build from the Linux agents as before: macOS with
the SDK plus Apple's `migcom` built for the host
(`deps/bootstrap-cmds.ts`), Windows with clang-cl and the auto-fetched
MSVC sysroot, FreeBSD/Android with their sysroots. macOS and Windows
hosts work too.
- **Linking without archives.** bun's own objects and the dependencies'
objects go straight to the link; no `libbun-*.a`, no per-dep
`.a`/`.lib`. The dep objects are a lazy group (`link()`'s `lazyObjects`:
lld's `/start-lib … /end-lib`, i.e. taken only if referenced — a static
library's semantics minus the file). That matters on Windows: COFF
linkers discard unreferenced code only at COMDAT granularity, so an
object with plain sections that nothing calls (any NASM output —
BoringSSL's AES-GCM-SIV asm is never called on Windows by BoringSSL's
own design) would otherwise be linked whole; upstream and Chromium rely
on archive member selection for the same thing. The group reaches
lld-link through clang-cl as `/clang:-Wl,@<exe>.lazy.rsp`. On ELF/Mach-O
the objects simply follow bun's in `$in` (those linkers dead-strip per
section).
- **Windows: `/lld-allow-duplicate-weak`.** WTF/JSC reference bun's
hooks (`WTFTimer__*`, `Bun__errorInstance__finalize`,
`Bun__reportUnhandledError`) as `__attribute__((weak))`; COFF has no
weak undefined symbol, so each referencing TU carries a weak external
with its own absolute-0 default and lld-link (MSVC mode) reports two
such TUs as a duplicate symbol even though bun's strong definition wins
— which ThinLTO importing `RunLoop::TimerBase::start()` into a JSC
module produces. lld-link's switch for exactly that check is on for
bun's and the JSC test programs' links (the latter previously used
`/force:multiple`); duplicate *strong* definitions still error. It
becomes a no-op once lld-link accepts several weak references to one
symbol (fixed in bun's LLVM toolchain) and is to be dropped then.

Build-system changes that came along:
- `ninja.ts` declares every build-dir output under its absolute path as
well, so a header a compiler depfile names absolutely resolves to its
generator and its includers recompile in the same run (was one build
late; affected bun's own `codegen/` too).
- `ninja_required_version` is 1.11 (validations). One phony per
order-only group instead of repeating generated-header lists on every
compile edge.
- One `dep_codegen` rule (`stream.ts --cwd/--env/--stdout`) for all dep
generators; `host_cc`/`host_cxx`/`host_link` for host tools;
`hostCc`/`hostCxx` are the plain clang drivers for any Windows target;
`-fsanitize=address` is part of the target link flags; tarball sources
carry a `sha256`; dep fetches print `[name] … (elapsed)`.
- Tools that assumed a prebuilt layout now read the build:
`scripts/jsc-exception-lint` takes JSC's TUs from
`compile_commands.json`; `bun-inspector-protocol`'s generator reads our
`CombinedDomains.json`; `.vscode/c_cpp_properties.json` just points at
the compile database.

### Bugs and misconfigurations on main that this fixes

Found by diffing compile lines against WebKit's cmake and dissecting
main's release binaries target by target:

- **windows-arm64: JSC compiled with FP contraction.** JSC's CMakeLists
sets `-ffp-contract=off -fno-slp-vectorize` for the whole target;
clang-cl ignores the GNU spellings and cmake's probe dropped them, so
the Windows prebuilt never had them. On arm64 that fused `Date`
arithmetic (`setNewValueFromTimeArgs`, `millisecondsFromComponents`,
`dateProtoFuncSetYear`, …) into `fmadd`, i.e. different rounding than
every other platform and than the JIT. Now passed as
`/clang:-ffp-contract=off /clang:-fno-slp-vectorize`.
- **Stack protector depended on the host compiler's vendor default.**
Nothing stated a policy, so CI (apt.llvm.org clang) shipped without it
while a build on Arch/Alpine/Fedora-packaged clang got
`-fstack-protector-strong` in every eligible function (62k canary checks
vs 161), and the musl JSC prebuilt (Alpine clang) had it while no other
target did. `-fno-stack-protector` is now explicit on unix.
- **PIC depended on the host compiler's default for deps.** bun's own
objects were `-fno-pic`, vendored deps got whatever the building clang
defaults to. CI's clang defaults to non-PIE so release artifacts were
unaffected, but on hosts whose clang defaults to PIE (Arch, Fedora,
Alpine, Homebrew) every dep was PIC: `.data.rel.ro` 541 KB instead of
109 KB and 4–7% more pages touched at startup. Every dep now gets bun's
PIC policy explicitly.
- **windows-arm64 tuned for Ampere.** `-mtune=ampere1` (copied from the
Linux server lane) padded every function and loop to 64 bytes on
Snapdragon hardware; MSVC, Chromium and Rust use generic tuning there.
Dropped; `-march=armv8-a+crc` unchanged.
- **Windows: the exe's import library overwrote the object archive.**
`bun.exe` exports symbols, so lld-link wrote `bun-profile.lib`, the same
path as the object archive `cpp-only` mode produces. It now goes to
`obj/<exe>.import.lib`.
- **Generated headers were one build late.** A generated header named
absolutely in a depfile didn't match its relative ninja output, so
includers recompiled on the *next* run (bun's `codegen/` headers too).
Fixed in `ninja.ts` as above.
- **FreeBSD/Android shipped 13 MB of ICU data they never load.** Only
the Linux and Windows prebuilts filtered and compressed ICU data; every
non-macOS target now does.
- **With a warm ccache, the second build of a fresh build dir recompiled
hundreds of objects (macOS, Windows).** The build exported
`CCACHE_FILECLONE=1`; entries stored that way are raw files, and a hit
is materialized by clone (APFS) or CopyFile (Windows), both keeping the
entry's mtime, so objects came out older than headers generated in the
same run. Dropped, plus `CCACHE_NAMESPACE=bun` so the raw entries
already in everyone's cache are never hit again.
- **`bun run build` never reached a no-op with an isolated-layout
`node_modules`.** The install edge declared
`node_modules/<dep>/package.json` as outputs; ninja pre-creates output
directories, so `node_modules/<dep>/` existed before `bun install` ran,
bun's isolated linker skipped the symlink, and install (plus the
esbuild/cargo edges behind it) re-ran on every build. It now declares
the `node_modules/<dep>` entry itself.
- **Links were serialized through ninja's console pool.** `link` was a
`pool = console` rule (depth 1), so once the graph had more than one
executable (bun, testFFI, JSC's LLInt extractors) bun's link waited
behind the others — ~25 s per release lane. Links are ordinary edges
now; the smoke test and ClassInfo check became ninja validations of the
link.
- **Every build after a build-script edit configured twice.** ninja
judges its `regen` edge by the mtime it recorded for `build.ninja`, not
the file's, so the manifest build.ts had just refreshed still looked
stale and ninja ran configure again (`[0/1] reconfigure`). Configure now
stamps the manifest and `ninja -t restat`s it.
- **bun.exe exported bmalloc's API and libpas' `g_config`.** bmalloc's
`BEXPORT` is `__declspec(dllexport)` even in a static build (WTF's macro
has the fork's carve-out, bmalloc's doesn't); 23 stray exports on top of
the intended Node-API/V8/libuv/llhttp set (same on main's prebuilt).
Found by the new export check; fixed with `-DBEXPORT=`.
- **Debug builds ran ~93 static initializers from the generated
classes.** `ZigGeneratedClasses.cpp` initialized each `extern "C"
<Type>__ptrOffset` from a non-`constexpr` `offsetOfWrapped()`; `-O2`
folded them, `-O0` ran them at startup. `constexpr` now, so they're
constant-initialized in every build (found by the new initializer
audit).
- **bun.exe ran in the Windows Vista compatibility context.** Its
manifest had no `<compatibility>`/`<trustInfo>` section, so Windows
applied Vista-era behavior (version APIs capped at 6.2, PCA monitoring)
to bun and every addon in-process. Now declares Windows 7–11 and
`asInvoker`, like node.exe; one visible effect is `process.report`'s
`header.osRelease` reporting `10.0` instead of `6.1` on Windows 10/11
(`os.release()` was already right, it uses `RtlGetVersion`). Found by
comparing against node's binaries.
- **Linux/FreeBSD exported four bun-internal `napi_internal_*` helpers**
through the `napi*` glob in the version script (macOS/Windows didn't).
Renamed out of the `napi_` namespace.
- **WebKit's own warning set wasn't applied when compiling it** (once
JSC is built here rather than by cmake): `-Wall -Wextra …
-Werror=undefined-inline/-internal` and the `-Wno-*` upstream carries
(e.g. clang 21's `-Wcharacter-conversion`) now match
WebKitCompilerFlags.cmake / OptionsMSVC.cmake.

		[2132]<a title='Build JavaScriptCore and ICU from source in bun's own build graph on every target (#41330)

JavaScriptCore, WTF, bmalloc — and, on every target except macOS, ICU —
are compiled from source inside bun's own ninja graph, like every other
vendored dependency, instead of being downloaded as a prebuilt
`bun-webkit-*` tarball. This is the default for every build, local and
CI; `--webkit=prebuilt` remains as an explicit opt-in.

### What changes

**CI**
- All 13 `build-bun` lanes (Linux x64/arm64 glibc + baseline + musl +
ASAN, Android, FreeBSD, macOS x64/arm64, Windows x64/arm64) compile JSC
in the same graph as bun's own C++; no
`libJavaScriptCore.a`/`libWTF.a`/`libbmalloc.a` step — the objects go
straight into the same archive/link as bun's.
- A WebKit change no longer needs a prebuilt to be published before bun
can build against it: bump `WEBKIT_VERSION` to any commit pushed to
oven-sh/WebKit.
- `build-bun` steps take ~1–2.5 min longer per target. Binary sizes: see
the table below (nothing grew; FreeBSD/Android −13 MB from ICU data
packing, windows-arm64 −3.5 MB, the rest under 2 MB).
- Build images: `bootstrap.sh` v42 adds `flex`/`bison` (host `migcom`
for the macOS lanes). Linux images are baked as a Buildkite job on a
fresh machine of the target distro plus a `wait-for-image` step, instead
of an instance driven over SSH from the hosted agent.
- `build-bun` is a plain full build now (the `archive-link` mode is
removed): bun's objects go straight into the link as in a local build,
and the per-lane `libbun-*.a.gz` / `libbun_runtime.a.gz` / dep-lib
artifact uploads, which nothing consumed, are gone. `cpp-only` keeps its
archive for the split pipeline. The precompiled header is built whenever
C++ is compiled (previously skipped for CI + full).
- `bootstrap.ps1` v23: ruby and zstd for native from-source builds on
the Windows images, and LLVM 21.1.8 installed from its release installer
(scoop's `llvm@21.1.8` now generates a non-existent `.msi` URL).
- Buildkite canvas: `verify-baseline` and `trace-order` are drawn beside
each target's build group instead of inside it (from #41408; no
scheduling change).

**Local development**
- `bun bd` / `bun run build` compile JSC too (fetched by ninja like
every dep, ~35 MB sparse; the first build of a build dir pays ~2 min for
JSC, then it is incremental and ccache-friendly). Host tools needed:
`ruby`, `python3`, `perl` (JSC's generators), `zstd` (ICU data,
non-macOS targets), and `flex`/`bison` only when cross-compiling a macOS
target from Linux (a Mac uses Xcode's `mig`).
- Release builds are LTO by default everywhere (what CI ships);
`--lto=off` for fast relinks. The `btg` profile is gone (it was "release
+ LTO"). On a native macOS or Windows host whose rustc LLVM is newer
than clang's (today: nightly LLVM 22 vs Homebrew llvm@21), the Rust↔C++
cross-language step is skipped and each half LTOs on its own — Apple's
ld runs LTO through clang's libLTO, which can't read newer bitcode and
has no lld to swap in; CI cross-compiles both from Linux with rustc's
lld and keeps full cross-language LTO.
- Working on JSC itself: `--local-deps=WebKit=<your clone>` on any
profile, like every other dep; `bun run build:local` is that with
`$BUN_WEBKIT_PATH`. The `debug-local`/`release-local` profiles and the
nested-cmake WebKit build are removed. `vendor/WebKit` is the build's
own fetch, so clones live elsewhere.
- Upgrading WebKit: the build itself checks the fetched tree against
what `scripts/build/deps/webkit.ts` transcribes — `Sources.txt` against
the checked-in unified-bundle lists, and a canonical rendering of the
relevant CMake statements (generators, options, compiler flags) against
`webkit-cmake.snapshot` — and fails with a diff when a bump changes
them; `.claude/commands/upgrade-webkit.md` says where each kind of
change maps.

### How it works

- **One dep kind.** Every C/C++ dep is a `direct` spec in
`scripts/build/deps/*.ts`: source groups (each with its own
flags/includes/PCH), `steps` (generators, host tools, target
executables), `headers` (files written at configure). WebKit is the same
shape as zlib, just larger; the `custom` kind is gone.
- **WebKit** (`deps/webkit.ts` +
`deps/webkit-{bmalloc,wtf,jsc,llint,inspector}-sources.ts`): bmalloc,
WTF and JavaScriptCore as three source groups; JSC's TUs are the unified
bundles listed explicitly in `webkit-sources.ts` (as WebKit's bundler
forms them, regenerated on a bump) plus the `@no-unify` files; every
generator WebKit's cmake runs (create_hash_table LUTs,
bytecode/Air/yarr/wasm generators, JS builtins, inspector protocol,
GeneratePreferences, offlineasm via the two LLInt extractor executables,
MIG on macOS) is a step invoking the same script with the same
arguments; `cmakeconfig.h`, the `<JavaScriptCore/X.h>` / `<bmalloc/X.h>`
forwarding stubs and the bundle files are `headers` entries. Compile
flags reproduce OptionsJSCOnly / WebKitCompilerFlags / OptionsMSVC per
platform on top of bun's dep-global flags, so JSC gets bun's `-march`,
LTO, sanitizer and hardening settings. Nothing reads the WebKit tree at
configure time.
- **ICU** (`deps/icu.ts` + `deps/icu-sources.ts`, `icu-data.ts`):
`common`/`i18n` compiled in-graph; a host `icupkg`; the data file
filtered and its display-name items zstd-repacked with a trained
dictionary, decompressed on first use through
`src/jsc/bindings/bun_icu_decompress.cpp`. That scheme was already in
the Linux/Windows prebuilts; it now applies uniformly (Linux, musl,
Android, FreeBSD, Windows). macOS keeps the SDK's `libicucore`.
- **Link-time checks** run as ninja validations of bun's link on every
lane, all static (`scripts/build/verify-binary.ts`, expectations per
target in `binary-expectations.ts`): exported symbols vs the lists in
`src/`; the exact NEEDED / dylib / import-DLL set and the glibc (2.17) /
FBSD (1.7) symbol-version ceiling (un-numbered version nodes such as
`GLIBC_ABI_DT_RELR` count; Android's floor is bionic's `LIBC`…`LIBC_P` /
`LIBLOG`…`LIBLOG_O`, API 28); forbidden imports (`__cxa_throw`,
`__emutls_*`, …); every static initializer symbolized and matched
against the runtime's known ones (none may come from bun/JSC/WTF);
nx-stack / no-RWX / PIE / DllCharacteristics; debug-info shape; and no
symbol strongly defined by two link inputs (every input must be readable
by the scanning tool — under the rustc/clang LLVM skew the scan uses
rustup's `llvm-nm`, hence the `llvm-tools` component in
`rust-toolchain.toml`). Plus the existing `--revision` smoke test
(host-runnable targets only) and the JSC ClassInfo audit.
- **testFFI** (JSC's bun:ffi ABI test program) is compiled and linked by
`bun.ts` next to `bun` from the same objects and shipped in the CI
artifact; the test fails, not skips, if it is missing in CI.
- **Native macOS and Windows hosts** (which CI never exercises — every
lane cross-compiles from Linux) were built end to end: Xcode's `mig`,
clang-cl as the target compiler with clang as the host compiler, ICU
data packing and testFFI all work there.
- **Cross targets** build from the Linux agents as before: macOS with
the SDK plus Apple's `migcom` built for the host
(`deps/bootstrap-cmds.ts`), Windows with clang-cl and the auto-fetched
MSVC sysroot, FreeBSD/Android with their sysroots. macOS and Windows
hosts work too.
- **Linking without archives.** bun's own objects and the dependencies'
objects go straight to the link; no `libbun-*.a`, no per-dep
`.a`/`.lib`. The dep objects are a lazy group (`link()`'s `lazyObjects`:
lld's `/start-lib … /end-lib`, i.e. taken only if referenced — a static
library's semantics minus the file). That matters on Windows: COFF
linkers discard unreferenced code only at COMDAT granularity, so an
object with plain sections that nothing calls (any NASM output —
BoringSSL's AES-GCM-SIV asm is never called on Windows by BoringSSL's
own design) would otherwise be linked whole; upstream and Chromium rely
on archive member selection for the same thing. The group reaches
lld-link through clang-cl as `/clang:-Wl,@<exe>.lazy.rsp`. On ELF/Mach-O
the objects simply follow bun's in `$in` (those linkers dead-strip per
section).
- **Windows: `/lld-allow-duplicate-weak`.** WTF/JSC reference bun's
hooks (`WTFTimer__*`, `Bun__errorInstance__finalize`,
`Bun__reportUnhandledError`) as `__attribute__((weak))`; COFF has no
weak undefined symbol, so each referencing TU carries a weak external
with its own absolute-0 default and lld-link (MSVC mode) reports two
such TUs as a duplicate symbol even though bun's strong definition wins
— which ThinLTO importing `RunLoop::TimerBase::start()` into a JSC
module produces. lld-link's switch for exactly that check is on for
bun's and the JSC test programs' links (the latter previously used
`/force:multiple`); duplicate *strong* definitions still error. It
becomes a no-op once lld-link accepts several weak references to one
symbol (fixed in bun's LLVM toolchain) and is to be dropped then.

Build-system changes that came along:
- `ninja.ts` declares every build-dir output under its absolute path as
well, so a header a compiler depfile names absolutely resolves to its
generator and its includers recompile in the same run (was one build
late; affected bun's own `codegen/` too).
- `ninja_required_version` is 1.11 (validations). One phony per
order-only group instead of repeating generated-header lists on every
compile edge.
- One `dep_codegen` rule (`stream.ts --cwd/--env/--stdout`) for all dep
generators; `host_cc`/`host_cxx`/`host_link` for host tools;
`hostCc`/`hostCxx` are the plain clang drivers for any Windows target;
`-fsanitize=address` is part of the target link flags; tarball sources
carry a `sha256`; dep fetches print `[name] … (elapsed)`.
- Tools that assumed a prebuilt layout now read the build:
`scripts/jsc-exception-lint` takes JSC's TUs from
`compile_commands.json`; `bun-inspector-protocol`'s generator reads our
`CombinedDomains.json`; `.vscode/c_cpp_properties.json` just points at
the compile database.

### Bugs and misconfigurations on main that this fixes

Found by diffing compile lines against WebKit's cmake and dissecting
main's release binaries target by target:

- **windows-arm64: JSC compiled with FP contraction.** JSC's CMakeLists
sets `-ffp-contract=off -fno-slp-vectorize` for the whole target;
clang-cl ignores the GNU spellings and cmake's probe dropped them, so
the Windows prebuilt never had them. On arm64 that fused `Date`
arithmetic (`setNewValueFromTimeArgs`, `millisecondsFromComponents`,
`dateProtoFuncSetYear`, …) into `fmadd`, i.e. different rounding than
every other platform and than the JIT. Now passed as
`/clang:-ffp-contract=off /clang:-fno-slp-vectorize`.
- **Stack protector depended on the host compiler's vendor default.**
Nothing stated a policy, so CI (apt.llvm.org clang) shipped without it
while a build on Arch/Alpine/Fedora-packaged clang got
`-fstack-protector-strong` in every eligible function (62k canary checks
vs 161), and the musl JSC prebuilt (Alpine clang) had it while no other
target did. `-fno-stack-protector` is now explicit on unix.
- **PIC depended on the host compiler's default for deps.** bun's own
objects were `-fno-pic`, vendored deps got whatever the building clang
defaults to. CI's clang defaults to non-PIE so release artifacts were
unaffected, but on hosts whose clang defaults to PIE (Arch, Fedora,
Alpine, Homebrew) every dep was PIC: `.data.rel.ro` 541 KB instead of
109 KB and 4–7% more pages touched at startup. Every dep now gets bun's
PIC policy explicitly.
- **windows-arm64 tuned for Ampere.** `-mtune=ampere1` (copied from the
Linux server lane) padded every function and loop to 64 bytes on
Snapdragon hardware; MSVC, Chromium and Rust use generic tuning there.
Dropped; `-march=armv8-a+crc` unchanged.
- **Windows: the exe's import library overwrote the object archive.**
`bun.exe` exports symbols, so lld-link wrote `bun-profile.lib`, the same
path as the object archive `cpp-only` mode produces. It now goes to
`obj/<exe>.import.lib`.
- **Generated headers were one build late.** A generated header named
absolutely in a depfile didn't match its relative ninja output, so
includers recompiled on the *next* run (bun's `codegen/` headers too).
Fixed in `ninja.ts` as above.
- **FreeBSD/Android shipped 13 MB of ICU data they never load.** Only
the Linux and Windows prebuilts filtered and compressed ICU data; every
non-macOS target now does.
- **With a warm ccache, the second build of a fresh build dir recompiled
hundreds of objects (macOS, Windows).** The build exported
`CCACHE_FILECLONE=1`; entries stored that way are raw files, and a hit
is materialized by clone (APFS) or CopyFile (Windows), both keeping the
entry's mtime, so objects came out older than headers generated in the
same run. Dropped, plus `CCACHE_NAMESPACE=bun` so the raw entries
already in everyone's cache are never hit again.
- **`bun run build` never reached a no-op with an isolated-layout
`node_modules`.** The install edge declared
`node_modules/<dep>/package.json` as outputs; ninja pre-creates output
directories, so `node_modules/<dep>/` existed before `bun install` ran,
bun's isolated linker skipped the symlink, and install (plus the
esbuild/cargo edges behind it) re-ran on every build. It now declares
the `node_modules/<dep>` entry itself.
- **Links were serialized through ninja's console pool.** `link` was a
`pool = console` rule (depth 1), so once the graph had more than one
executable (bun, testFFI, JSC's LLInt extractors) bun's link waited
behind the others — ~25 s per release lane. Links are ordinary edges
now; the smoke test and ClassInfo check became ninja validations of the
link.
- **Every build after a build-script edit configured twice.** ninja
judges its `regen` edge by the mtime it recorded for `build.ninja`, not
the file's, so the manifest build.ts had just refreshed still looked
stale and ninja ran configure again (`[0/1] reconfigure`). Configure now
stamps the manifest and `ninja -t restat`s it.
- **bun.exe exported bmalloc's API and libpas' `g_config`.** bmalloc's
`BEXPORT` is `__declspec(dllexport)` even in a static build (WTF's macro
has the fork's carve-out, bmalloc's doesn't); 23 stray exports on top of
the intended Node-API/V8/libuv/llhttp set (same on main's prebuilt).
Found by the new export check; fixed with `-DBEXPORT=`.
- **Debug builds ran ~93 static initializers from the generated
classes.** `ZigGeneratedClasses.cpp` initialized each `extern "C"
<Type>__ptrOffset` from a non-`constexpr` `offsetOfWrapped()`; `-O2`
folded them, `-O0` ran them at startup. `constexpr` now, so they're
constant-initialized in every build (found by the new initializer

### How it works

- **One dep kind.** Every C/C++ dep is a `direct` spec in
`scripts/build/deps/*.ts`: source groups (each with its own
flags/includes/PCH), `steps` (generators, host tools, target
executables), `headers` (files written at configure). WebKit is the same
shape as zlib, just larger; the `custom` kind is gone.
- **WebKit** (`deps/webkit.ts` +
`deps/webkit-{bmalloc,wtf,jsc,llint,inspector}-sources.ts`): bmalloc,
WTF and JavaScriptCore as three source groups; JSC's TUs are the unified
bundles listed explicitly in `webkit-sources.ts` (as WebKit's bundler
forms them, regenerated on a bump) plus the `@no-unify` files; every
generator WebKit's cmake runs (create_hash_table LUTs,
bytecode/Air/yarr/wasm generators, JS builtins, inspector protocol,
GeneratePreferences, offlineasm via the two LLInt extractor executables,
MIG on macOS) is a step invoking the same script with the same
arguments; `cmakeconfig.h`, the `<JavaScriptCore/X.h>` / `<bmalloc/X.h>`
forwarding stubs and the bundle files are `headers` entries. Compile
flags reproduce OptionsJSCOnly / WebKitCompilerFlags / OptionsMSVC per
platform on top of bun's dep-global flags, so JSC gets bun's `-march`,
LTO, sanitizer and hardening settings. Nothing reads the WebKit tree at
configure time.
- **ICU** (`deps/icu.ts` + `deps/icu-sources.ts`, `icu-data.ts`):
`common`/`i18n` compiled in-graph; a host `icupkg`; the data file
filtered and its display-name items zstd-repacked with a trained
dictionary, decompressed on first use through
`src/jsc/bindings/bun_icu_decompress.cpp`. That scheme was already in
the Linux/Windows prebuilts; it now applies uniformly (Linux, musl,
Android, FreeBSD, Windows). macOS keeps the SDK's `libicucore`.
- **Link-time checks** run as ninja validations of bun's link on every
lane, all static (`scripts/build/verify-binary.ts`, expectations per
target in `binary-expectations.ts`): exported symbols vs the lists in
`src/`; the exact NEEDED / dylib / import-DLL set and the glibc (2.17) /
FBSD (1.7) symbol-version ceiling (un-numbered version nodes such as
`GLIBC_ABI_DT_RELR` count; Android's floor is bionic's `LIBC`…`LIBC_P` /
`LIBLOG`…`LIBLOG_O`, API 28); forbidden imports (`__cxa_throw`,
`__emutls_*`, …); every static initializer symbolized and matched
against the runtime's known ones (none may come from bun/JSC/WTF);
nx-stack / no-RWX / PIE / DllCharacteristics; debug-info shape; and no
symbol strongly defined by two link inputs (every input must be readable
by the scanning tool — under the rustc/clang LLVM skew the scan uses
rustup's `llvm-nm`, hence the `llvm-tools` component in
`rust-toolchain.toml`). Plus the existing `--revision` smoke test
(host-runnable targets only) and the JSC ClassInfo audit.
- **testFFI** (JSC's bun:ffi ABI test program) is compiled and linked by
`bun.ts` next to `bun` from the same objects and shipped in the CI
artifact; the test fails, not skips, if it is missing in CI.
- **Native macOS and Windows hosts** (which CI never exercises — every
lane cross-compiles from Linux) were built end to end: Xcode's `mig`,
clang-cl as the target compiler with clang as the host compiler, ICU
data packing and testFFI all work there.
- **Cross targets** build from the Linux agents as before: macOS with
the SDK plus Apple's `migcom` built for the host
(`deps/bootstrap-cmds.ts`), Windows with clang-cl and the auto-fetched
MSVC sysroot, FreeBSD/Android with their sysroots. macOS and Windows
hosts work too.
- **Linking without archives.** bun's own objects and the dependencies'
objects go straight to the link; no `libbun-*.a`, no per-dep
`.a`/`.lib`. The dep objects are a lazy group (`link()`'s `lazyObjects`:
lld's `/start-lib … /end-lib`, i.e. taken only if referenced — a static
library's semantics minus the file). That matters on Windows: COFF
linkers discard unreferenced code only at COMDAT granularity, so an
object with plain sections that nothing calls (any NASM output —
BoringSSL's AES-GCM-SIV asm is never called on Windows by BoringSSL's
own design) would otherwise be linked whole; upstream and Chromium rely
on archive member selection for the same thing. The group reaches
lld-link through clang-cl as `/clang:-Wl,@<exe>.lazy.rsp`. On ELF/Mach-O
the objects simply follow bun's in `$in` (those linkers dead-strip per
section).
- **Windows: `/lld-allow-duplicate-weak`.** WTF/JSC reference bun's
hooks (`WTFTimer__*`, `Bun__errorInstance__finalize`,
`Bun__reportUnhandledError`) as `__attribute__((weak))`; COFF has no
weak undefined symbol, so each referencing TU carries a weak external
with its own absolute-0 default and lld-link (MSVC mode) reports two
such TUs as a duplicate symbol even though bun's strong definition wins
— which ThinLTO importing `RunLoop::TimerBase::start()` into a JSC
module produces. lld-link's switch for exactly that check is on for
bun's and the JSC test programs' links (the latter previously used
`/force:multiple`); duplicate *strong* definitions still error. It
becomes a no-op once lld-link accepts several weak references to one
symbol (fixed in bun's LLVM toolchain) and is to be dropped then.

Build-system changes that came along:
- `ninja.ts` declares every build-dir output under its absolute path as
well, so a header a compiler depfile names absolutely resolves to its
generator and its includers recompile in the same run (was one build
late; affected bun's own `codegen/` too).
- `ninja_required_version` is 1.11 (validations). One phony per
order-only group instead of repeating generated-header lists on every
compile edge.
- One `dep_codegen` rule (`stream.ts --cwd/--env/--stdout`) for all dep
generators; `host_cc`/`host_cxx`/`host_link` for host tools;
`hostCc`/`hostCxx` are the plain clang drivers for any Windows target;
`-fsanitize=address` is part of the target link flags; tarball sources
carry a `sha256`; dep fetches print `[name] … (elapsed)`.
- Tools that assumed a prebuilt layout now read the build:
`scripts/jsc-exception-lint` takes JSC's TUs from
`compile_commands.json`; `bun-inspector-protocol`'s generator reads our
`CombinedDomains.json`; `.vscode/c_cpp_properties.json` just points at
the compile database.

### Bugs and misconfigurations on main that this fixes

Found by diffing compile lines against WebKit's cmake and dissecting
main's release binaries target by target:

- **windows-arm64: JSC compiled with FP contraction.** JSC's CMakeLists
sets `-ffp-contract=off -fno-slp-vectorize` for the whole target;
clang-cl ignores the GNU spellings and cmake's probe dropped them, so
the Windows prebuilt never had them. On arm64 that fused `Date`
arithmetic (`setNewValueFromTimeArgs`, `millisecondsFromComponents`,
`dateProtoFuncSetYear`, …) into `fmadd`, i.e. different rounding than
every other platform and than the JIT. Now passed as
`/clang:-ffp-contract=off /clang:-fno-slp-vectorize`.
- **Stack protector depended on the host compiler's vendor default.**
Nothing stated a policy, so CI (apt.llvm.org clang) shipped without it
while a build on Arch/Alpine/Fedora-packaged clang got
`-fstack-protector-strong` in every eligible function (62k canary checks
vs 161), and the musl JSC prebuilt (Alpine clang) had it while no other
target did. `-fno-stack-protector` is now explicit on unix.
- **PIC depended on the host compiler's default for deps.** bun's own
objects were `-fno-pic`, vendored deps got whatever the building clang
defaults to. CI's clang defaults to non-PIE so release artifacts were
unaffected, but on hosts whose clang defaults to PIE (Arch, Fedora,
Alpine, Homebrew) every dep was PIC: `.data.rel.ro` 541 KB instead of
109 KB and 4–7% more pages touched at startup. Every dep now gets bun's
PIC policy explicitly.
- **windows-arm64 tuned for Ampere.** `-mtune=ampere1` (copied from the
Linux server lane) padded every function and loop to 64 bytes on
Snapdragon hardware; MSVC, Chromium and Rust use generic tuning there.
Dropped; `-march=armv8-a+crc` unchanged.
- **Windows: the exe's import library overwrote the object archive.**
`bun.exe` exports symbols, so lld-link wrote `bun-profile.lib`, the same
path as the object archive `cpp-only` mode produces. It now goes to
`obj/<exe>.import.lib`.
- **Generated headers were one build late.** A generated header named
absolutely in a depfile didn't match its relative ninja output, so
includers recompiled on the *next* run (bun's `codegen/` headers too).
Fixed in `ninja.ts` as above.
- **FreeBSD/Android shipped 13 MB of ICU data they never load.** Only
the Linux and Windows prebuilts filtered and compressed ICU data; every
non-macOS target now does.
- **With a warm ccache, the second build of a fresh build dir recompiled
hundreds of objects (macOS, Windows).** The build exported
`CCACHE_FILECLONE=1`; entries stored that way are raw files, and a hit
is materialized by clone (APFS) or CopyFile (Windows), both keeping the
entry's mtime, so objects came out older than headers generated in the
same run. Dropped, plus `CCACHE_NAMESPACE=bun` so the raw entries
already in everyone's cache are never hit again.
- **`bun run build` never reached a no-op with an isolated-layout
`node_modules`.** The install edge declared
`node_modules/<dep>/package.json` as outputs; ninja pre-creates output
directories, so `node_modules/<dep>/` existed before `bun install` ran,
bun's isolated linker skipped the symlink, and install (plus the
esbuild/cargo edges behind it) re-ran on every build. It now declares
the `node_modules/<dep>` entry itself.
- **Links were serialized through ninja's console pool.** `link` was a
`pool = console` rule (depth 1), so once the graph had more than one
executable (bun, testFFI, JSC's LLInt extractors) bun's link waited
behind the others — ~25 s per release lane. Links are ordinary edges
now; the smoke test and ClassInfo check became ninja validations of the
link.
- **Every build after a build-script edit configured twice.** ninja
judges its `regen` edge by the mtime it recorded for `build.ninja`, not
the file's, so the manifest build.ts had just refreshed still looked
stale and ninja ran configure again (`[0/1] reconfigure`). Configure now
stamps the manifest and `ninja -t restat`s it.
- **bun.exe exported bmalloc's API and libpas' `g_config`.** bmalloc's
`BEXPORT` is `__declspec(dllexport)` even in a static build (WTF's macro
has the fork's carve-out, bmalloc's doesn't); 23 stray exports on top of
the intended Node-API/V8/libuv/llhttp set (same on main's prebuilt).
Found by the new export check; fixed with `-DBEXPORT=`.
- **Debug builds ran ~93 static initializers from the generated
classes.** `ZigGeneratedClasses.cpp` initialized each `extern "C"
<Type>__ptrOffset` from a non-`constexpr` `offsetOfWrapped()`; `-O2`
folded them, `-O0` ran them at startup. `constexpr` now, so they're
constant-initialized in every build (found by the new initializer
audit).

### What does this PR do?

Fixes the `x64-musl verify-baseline` failure on main ([build
110907](https://buildkite.com/bun/bun/builds/110907)): `llint_op_wide16
[INVLPGB] (1 insns)` — a false positive, not a real post-baseline
instruction.

The static scanner decoded all of `.text` in one linear sweep. JSC's
LLInt emits a 4-byte `.int <opcode id>` in front of every `llint_op_*`
label (`LLINT_EMBEDDED_OPCODE_ID`, x86_64), so after each of those the
sweep decoded a few bytes of garbage before falling back into sync, and
*what* the garbage decoded as depended on the following bytes — here a
`%rip`-relative displacement, which moves with link layout. That is why
the PR that last touched this passed and the squash onto a newer main
did not, and why `allowlist-x64.txt` had accumulated three `llint_op_*`
blanket entries "as they trip".

Now the decoder restarts at every symbol start: an instruction that
would straddle a symbol boundary is discarded and decoding resumes at
the symbol. The three whack-a-mole entries are removed; README/CLAUDE.md
describe the new behaviour.

		<a title='Add new bindings generator; port `SSLConfig` (#23169)

Add a new generator for JS → Zig bindings. The bulk of the conversion is
done in C++, after which the data is transformed into an FFI-safe
representation, passed to Zig, and then finally transformed into
idiomatic Zig types.

In its current form, the new bindings generator supports:

* Signed and unsigned integers
* Floats (plus a “finite” variant that disallows NaN and infinities)
* Strings
* ArrayBuffer (accepts ArrayBuffer, TypedArray, or DataView)
* Blob
* Optional types
* Nullable types (allows null, whereas Optional only allows undefined)
* Arrays
* User-defined string enumerations
* User-defined unions (fields can optionally be named to provide a
better experience in Zig)
* Null and undefined, for use in unions (can more efficiently represent
optional/nullable unions than wrapping a union in an optional)
* User-defined dictionaries (arbitrary key-value pairs; expects a JS
object and parses it into a struct)
* Default values for dictionary members
* Alternative names for dictionary members (e.g., to support both
`serverName` and `servername` without taking up twice the space)
* Descriptive error messages
* Automatic `fromJS` functions in Zig for dictionaries
* Automatic `deinit` functions for the generated Zig types

Although this bindings generator has many features not present in
`bindgen.ts`, it does not yet implement all of `bindgen.ts`'s
functionality, so for the time being, it has been named `bindgenv2`, and
its configuration is specified in `.bindv2.ts` files. Once all
`bindgen.ts`'s functionality has been incorporated, it will be renamed.

This PR ports `SSLConfig` to use the new bindings generator; see
`SSLConfig.bindv2.ts`.

(For internal tracking: fixes STAB-1319, STAB-1322, STAB-1323,
STAB-1324)
